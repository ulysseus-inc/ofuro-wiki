# 不審なログイン試行の検知と通知

Issue #117。#93（ログイン試行の制限とアカウントロック）で**攻撃を止められる**ようになったが、
**起きたことに気づく手段が無い**。ロックは自動解除されるため放置しても被害は限定的だが、
攻撃の継続に気づかず対処が遅れる。

関連: [`logging.md`](logging.md)（記録の設計）/ [`deploy/README.md`](deploy/README.md)（対処手順）

---

## 1. 全体像

```
     ┌──────────────────────────┐
     │ AuthService              │ → audit_logs（auth.signin.failed / auth.locked）
     │ GqlThrottlerGuard        │ → メモリ上のカウンタ（429・未登録アドレスへの試行）
     └──────────────────────────┘
                  ↓ 5分ごと
     ┌──────────────────────────┐
     │ 検知バッチ（@Cron）        │  直近1時間を集計し、しきい値と比べる
     └──────────────────────────┘
                  ↓ 条件を満たしたら
     ┌──────────────────────────┐
     │ audit_logs に security.alert を記録  ← **必ず行う**
     │ Admin 全員へメール送信              ← SMTP 設定時のみ
     └──────────────────────────┘
```

**記録が先、通知が後。** メールが設定されていない閉域環境でも、
監査ログ画面（#90）から検知の事実を追える。

---

## 2. 検知条件

**5分ごとに、直近60分を評価する。**

窓は移動する。ある事象は発生から60分間だけ集計に入り、その後は自動的に外れる。
したがって「検知され続ける時間」は条件の満たされ方によって**55〜60分の揺らぎ**が出る。
実害は無いが、監査ログの並びを見たときに不自然に見えないよう明記しておく。

| 種別 | 条件（既定値） | 深刻度 | 想定する攻撃 | データ源 |
|---|---|:--:|---|---|
| **A. 標的型** | 同一アカウントが60分に **3回以上ロック** | **MEDIUM** | 特定アカウントへの集中攻撃 | `audit_logs` `auth.locked` |
| **B. スプレー** | 60分に **20アカウント以上**でログイン失敗 | **HIGH** | パスワードスプレー | `audit_logs` `auth.signin.failed` |
| **C. 総当たり / DoS** | 60分に **429 が100回以上** | **MEDIUM** | 連射・DoS | メモリ上のカウンタ |
| **D. アカウント列挙** | 60分に **50回以上**、存在しないアドレスへの試行 | **LOW** | 偵察 | メモリ上のカウンタ |

### 2.0 深刻度（severity）

`LOW` / `MEDIUM` / `HIGH` / `CRITICAL` の4段階を `security.alert` に持たせる。

**メール本文の「緊急度」と同じ判断に揃える。** 画面と本文で食い違うと、どちらを信じるか迷う。

| 深刻度 | 割り当て | 判断の根拠 |
|---|---|---|
| `LOW` | D | 存在しないアカウントへの試行。突破されようがない |
| `MEDIUM` | A・C | A はロックが効いている / C はレート制限が弾いている。**どちらも防げている** |
| `HIGH` | B | **ロックが発生しないまま進行**し、弱いパスワードのアカウントが破られうる |
| `CRITICAL` | （未使用） | 「実際に突破された」を検知できるようになったときのために空けておく |

> **なぜいま使わない段階を用意するのか**: 後から段階を増やすと、
> **過去に記録した `security.alert` の意味が変わる**。空けておく方が安全。

将来、画面での色分け（赤 / 黄）や、深刻度による通知手段の切り替えに使える。

**B が最も重要。** パスワードスプレー（多数のアカウントに少数回ずつ試す）は
**ロックが1件も発生しないまま進行する**ため、ロックだけを見ていると検知できない。

### 2.0.1 条件C が数える 429 は2種類ある

**429 は2箇所から出る。両方を数える。**

| 出どころ | 何を数えた結果か |
|---|---|
| `GqlThrottlerGuard` | **リクエスト数**（60回/5分・300回/分） |
| **`AuthService.assertSigninAllowed`** | **失敗回数**（5回/5分） |

⚠️ **総当たり攻撃で最も多く出るのは後者。** 攻撃者が速度を落とせば
ガードの制限（60回/5分）には達しないため、そちらの 429 は一度も出ない。
後者を数えなければ、**攻撃速度を落とすだけで条件Cを完全に回避できる。**

しかも後者は**パスワード照合の前**に投げられるため、
監査ログ（`auth.signin.failed`）にも残らない。**数える場所はここしかない。**

> なおこの攻撃は条件A（ロックの多発）でも捕捉できる。
> 条件Cを直す価値は「**検知が約30分から5分に早まる**」ことと、
> 「429 の多発という事実が正しく通知される」ことにある。

### 2.1 なぜ C・D をメモリで数えるのか

**どちらも「防げている」事象**であり、監査証跡として保全する必要がない。

- **C（429）**: レート制限が弾いている。パスワードの照合まで到達していない
- **D（未登録アドレス）**: 存在しないアカウントなので、突破されようがない

窓は1時間なのでメモリで足りる。再起動で消えるが、攻撃が続いていれば数分で再び閾値に達する。
一方、**攻撃中は大量に発生する**ため、監査ログに1件ずつ書くと DB が膨らむ。

> **数値の見積もり**: レート制限はサインインを「IP + メールアドレス」単位で数えるため、
> アドレスを変えれば1つの IP から多数の試行ができる。全体制限（60秒/300リクエスト）に
> かかるまで、**1時間あたり最大 18,000 回**。1件500バイトで見積もっても 9MB/時。
> 3年保持する監査ログに入れる種類のものではない。

### 2.2 ⚠️ 条件B の限界（実装前に把握しておくこと）

`auth.signin.failed` の記録には**60秒の重複抑止**がかかっており、抑止の単位が経路で異なる。

| 失敗の種類 | 抑止のキー | 条件B への影響 |
|---|---|---|
| **既存アカウント × パスワード誤り** | **抑止なし**（全件記録） | ✅ **そのまま数えられる** |
| 存在しないアドレス / パスワード未設定 | `IP + 理由`（**アドレスを含まない**） | ❌ **1つの IP から1分に1件しか残らない** |
| ロック中のアカウントへの試行 | `IP + "locked" + ユーザーID` | ユーザー単位なので実害小 |

つまり **「実在するアカウントを狙ったスプレー」は正しく検知できる**が、
**「存在しないアドレスを含む列挙」は監査ログ上でほぼ消える。**

`auth.service.ts` のコメントは「総当たり・アカウント列挙はここに現れる（#117 の主要な検知材料）」
と書いているが、**抑止キーにアドレスが入っていないため、実際には現れない。**

**対処**: 抑止キーを変えて記録量を増やすのではなく（2.1 の理由）、
**条件D として別に数える。** 危険度の高い「実在アカウントへのスプレー」は条件Bが押さえ、
偵察は条件Dが押さえる、という分担にする。

## 3. 通知

### 3.1 経路はメールのみ

| 経路 | 判断 | 理由 |
|---|:--:|---|
| **メール** | **採用** | `MailService`（nodemailer）が実装済み |
| Slack / Teams | 不採用 | #94 をスコープ外とした（サーバーが社内文書の中身を社外へ送る性質） |
| アプリ内通知 | 不採用 | 下記 |

**アプリ内通知を採らない理由**

1. **メールと役割が重複する。** Admin がサインインして初めて見え、バッジの更新も30秒ごとの
   ポーリング。「深夜に届いてもその場で判断できる」という狙いに対し能動性がない
2. **受信箱の性質が違う。** 既存の通知9種は招待・メンション・コメントで、すべて
   **「人が人に何かした」という業務の通知**。緊急度の異なるものを同じ箱に入れると、
   箱全体の緊急度が下がる
3. **フロントエンドに波及する。** GraphQL の enum 拡張 + 945行のリストへの分岐追加 + i18n + E2E

### 3.2 宛先

`users.is_admin` が真のユーザー**全員**。`ADMIN_EMAIL` だけに限定しない
（Admin は運用中に追加されるため）。

システム内部アカウント（`isSystem`）は除く。

### 3.3 SMTP が未設定のとき

**送信をとばし、記録は必ず残す。** 例外にしない。

**検知が動かなくなるのが最悪**であり、通知できないことは次善の状態にすぎない。

> ⚠️ **5分ごとに警告を出さないこと。** 未設定は起動時に `MailService` が1回警告しており、
> 検知バッチが繰り返し出すと**アプリログが警告で埋まり、本当の異常が見えなくなる**。
> 未設定の事実は `detail.meta.mailStatus = "disabled"` に残るので、そちらで追える。

### 3.4 本文

**深夜に届いてもその場で判断できるよう、対処の要約を本文に書く。**
種別ごとに対処が異なるため、文面を分ける。全文は Issue #117 に記載。

共通の構成:

```
種別  : 何が起きているか（一言で）
対象  : 対象アカウント（種別Aのみ）
状況  : 数字（**アカウント数と総回数の両方**・期間）
発信元: IP と回数（上位3件 + 「ほか N 件」）

▼ 対処の目安
1. 緊急度と、いま侵入されているのかどうか
2〜4. 具体的な手順（プロキシで遮断 / 本人に連絡 / SSO へ切り替え）

※ 誤検知の可能性があればその旨
詳細: docs/deploy/README.md#攻撃を検知したときの対応
```

**「緊急度」と「侵入されたのか」を先頭に書く。** 深夜に叩き起こされた人が最初に知りたいのはそこ。

### 3.5 数字は「広さ」と「深さ」を両方書く

種別Bで「24アカウント」とだけ書くと、**1アカウントあたり1回なのか100回なのか**が分からない。
対処の緊急度はそこで変わる（前者は偵察、後者は本気の総当たり）。

```
状況  : 直近60分に 24 アカウントでログイン失敗（合計 312 回）
                  ↑広さ                          ↑深さ
```

**発信元は上位3件まで。** 100件並べても人間は読まない。
**メールと監査ログで同じ情報量にする**（片方にしか無いと、どちらを見ればよいか迷う）。

## 4. 抑制と終息通知

攻撃中は5分ごとに条件を満たすため、そのまま送ると**通知スパムになり逆に無視される**。

| 規則 | 内容 |
|---|---|
| **同一条件につき60分に1通** | 種別 + 対象（種別Aはアカウント）が同じなら送らない |
| **終息通知** | **該当する事象が30分間まったく無くなったら**「収まりました」を1通 |

### 4.0 終息判定にヒステリシスを設ける

**「条件を満たさなくなったら即座に終息」としてはいけない。**

```
11:00  攻撃 → 検知（通知）
11:04  攻撃が止む
11:05  条件を外れる → 終息通知 ①
11:07  攻撃が再開
11:10  再び検知 → 通知 ②
11:14  また止む
11:15  終息通知 ③        ← 15分で3通。通知の価値が失われる
```

**断続的な攻撃は珍しくない**（ツールがリトライする・複数の IP を順に使う）。
そのたびに検知と終息を往復すると、**受け手は通知を無視するようになる。**
通知の目的は「気づいてもらうこと」なので、無視されたら機能していないのと同じ。

**判定**: 直近 **30分**（`ALERT_RESOLVE_QUIET_MINUTES`）に、
その条件に該当する事象が **1件も無い**こと。

- 種別A・B: `audit_logs` に該当する `auth.locked` / `auth.signin.failed` が無い
- 種別C・D: メモリ上のカウンタが30分間ゼロ

> **「条件を満たさない」ではなく「事象が無い」で判定する。** 前者だと、
> しきい値を下回っただけの**攻撃継続中に終息通知が飛ぶ**
> （例: ロックが3回→2回に減っただけ）。

### 4.1 抑制の状態をどこに持つか

**`audit_logs` そのものを状態とする。新しいテーブルを作らない。**

- 送信前に「直近1時間に同じ種別・同じ対象の `security.alert` があるか」を問い合わせる
- あれば送らない

**再起動しても重複しない**のが利点。メモリに持つと、再起動のたびに同じ警報が再送される。

終息判定も同じ考え方で、「終息を出していない `security.alert` があり、
かつ 4.0 の静穏条件を満たす」なら `security.alert.resolved` を記録して送る。

> C・D のカウンタはメモリだが、**抑制の状態は永続**という非対称は意図的。
> カウンタが消えても再計上されるだけだが、抑制状態が消えると**利用者にメールが二重に届く**。

## 5. 監査ログへの記録

[`logging.md`](logging.md) の記録一覧マトリクスに2行追加する。

| action | 実行者 | 対象ID | 対象名 | 記録経路 |
|---|:--:|:--:|:--:|---|
| `security.alert` | — | ✅※ | — | IntrusionDetectionService（`system`） |
| `security.alert.resolved` | — | ✅※ | — | 同上 |

※ 対象IDは種別Aのみ（ロックされたアカウント）。B・C・D は対象を特定しないため `—`。

実行者は `system`（`audit.cleanup` と同じ扱い）。

`detail.meta` に入れるもの:

```json
{
  "kind": "B",
  "severity": "HIGH",
  "windowMinutes": 60,
  "threshold": 20,
  "accounts": 24,
  "totalFailures": 312,
  "sampleAccounts": [
    "user1@example.com", "user2@example.com", "user3@example.com",
    "user4@example.com", "user5@example.com"
  ],
  "topIps": [
    { "ip": "203.0.113.5", "count": 61 },
    { "ip": "198.51.100.9", "count": 12 },
    { "ip": "192.0.2.44", "count": 3 }
  ],
  "otherIpCount": 3,
  "mailStatus": "success",
  "recipients": 2,
  "delivered": 1,
  "rejected": 1
}
```

| 項目 | なぜ必要か |
|---|---|
| `severity` | 画面での色分け・将来の通知手段の切り替え |
| `accounts` + `totalFailures` | **広さと深さの両方**。片方だけでは対処の緊急度を判断できない（3.5） |
| **`sampleAccounts`（最大5件）** | **数字だけでは調査を始められない。** 「どのアカウントか」が分かると、退職者のアカウントか・特定部署に偏っているか等がすぐ見える。全件は残さない（攻撃対象一覧を作る意味がない） |
| `topIps`（**上位3件**）+ `otherIpCount` | 発信元が1つに偏っていればプロキシで遮断できる。3件を超えると人間は読まない |
| **`mailStatus`** | 下記 |
| `recipients` / **`delivered`** / **`rejected`** | **送ろうとした人数・実際に受理された人数・拒否された人数**（下記） |

### 5.1 `mailStatus` は3値にする

**真偽値では足りない。** 運用では「なぜ送られなかったか」を知りたくなる。

| 値 | 意味 | 運用上の判断 |
|---|---|---|
| `success` | 送信した | — |
| `disabled` | **SMTP が未設定** | 設定すれば直る。**設計どおりの動作** |
| `failed` | 設定はあるが**送信に失敗** | **異常。** SMTP サーバの疎通・認証を確認する |

`disabled` と `failed` は対処がまったく違う。`false` にまとめると区別できない。

### 5.2 「送った人数」と「届いた人数」を分けて残す

**一部の宛先が拒否されても、送信そのものは成功する**（`sendMail` は例外を投げない）。
送った人数だけを記録すると、**1人にも届いていないのに成功に見える。**

| 項目 | 意味 |
|---|---|
| `recipients` | 送ろうとした Admin の人数 |
| **`delivered`** | **実際に受理された人数** |
| **`rejected`** | **SMTP に宛先として拒否された人数** |

> ⚠️ **`rejected` は「宛先が拒否された」だけを意味する。**
> 接続不能・認証失敗といった**送信そのものの失敗を `rejected` に数えてはいけない。**
> 「2件拒否」と記録すると、運用者は **Admin のアドレスが無効だと考えて
> アカウントの整理を始める**。実際は SMTP サーバー側の問題であり、直す場所が違う。
> 送信が成立していない事実は `mailStatus: "failed"` が示す（`rejected` は 0）。

- `delivered` が **0 なら `mailStatus: "failed"`**（誰にも届いていない）
- 一部だけ拒否なら `success` のまま、`rejected` に件数を残す

> **現実に起きる状況**: 退職した Admin のアカウントが残っており、
> そのアドレスが既に廃止されている。**運用中に自然に発生する。**
>
> なお `to` には差出人自身を入れているため、**差出人を宛先として数えないこと。**
> 数えると「誰にも届いていないのに `delivered: 1`」になる。

**「検知したがメールが飛んでいない」状態を後から判別できないと、
「通知が来なかった＝攻撃が無かった」と誤解される。**

## 6. 設定

| 環境変数 | 既定値 | 意味 |
|---|:--:|---|
| `ALERT_WINDOW_MINUTES` | `60` | **集計の窓**。全種別で共通 |
| `ALERT_LOCK_THRESHOLD` | `3` | 種別A: 窓内のロック回数 |
| `ALERT_SPRAY_ACCOUNT_THRESHOLD` | `20` | 種別B: 窓内の失敗アカウント数 |
| `ALERT_THROTTLE_THRESHOLD` | `100` | 種別C: 窓内の429回数 |
| `ALERT_UNKNOWN_EMAIL_THRESHOLD` | `50` | 種別D: 窓内の未登録アドレス試行数 |
| `ALERT_RESOLVE_QUIET_MINUTES` | `30` | 終息と判定するまでの静穏時間（4.0） |
| `ALERT_DISABLED` | `false` | 検知そのものを止める |

しきい値は**社内 Wiki の規模を想定した初期値**。運用しながら調整する。
管理画面には出さない（サーバー全体の設定であり、運用者がデプロイ時に決めるもの）。

> `ALERT_WINDOW_MINUTES` を変えることは実運用ではまず無いが、
> **しきい値だけ設定可能で窓が固定だと、しきい値の意味が読み手に伝わらない。**
> 「60分に3回」の 60 がどこから来るのかを設定で示す。

### 6.1 `ALERT_DISABLED` が真なら起動時に1行残す

```
[IntrusionDetection] WARN  検知は無効化されています（ALERT_DISABLED=true）
```

**運用で最も怖いのは「止めたまま忘れる」こと。**
攻撃されても何も起きず、しかも**何も起きないこと自体が正常に見える。**

起動ログに残しておけば、障害調査で必ず目に入る。
`security.alert` が長期間ゼロのとき、「攻撃が無かった」のか「止めていた」のかを区別できる。

> 起動時の1行にとどめ、5分ごとには出さない（3.3 と同じ理由）。

## 7. 失敗したときの扱い

**検知バッチの失敗でアプリを止めない。**

集計・送信のいずれで失敗しても例外を投げず、`logger.error` で必ず残す。
これは [`logging.md`](logging.md) で監査ログに定めた方針と同じで、
**「記録・通知の失敗が、本来の機能を巻き添えにしない」**ことを優先する。

ただし**失敗した事実は必ず残す。** 黙って何もしないのが最悪。

## 8. 対応しないこと

| やらないこと | 理由 |
|---|---|
| **アプリ内での IP ブロック** | リバースプロキシ / ファイアウォールの仕事。プロキシ配下では正しい IP が取れない場合があり、攻撃者は IP を変えてくる。**手順書での案内にとどめる** |
| アプリ内通知・バッジ | 3.1 の通り |
| しきい値の管理画面設定 | 運用者がデプロイ時に決めるもの。画面を増やすと検証範囲も増える |
| 検知の即時性（リアルタイム） | 5分の遅れは、人間が対処を始めるまでの時間に比べて無視できる |

---

## 9. 恒久対策

**最も効くのは SSO（#89）。** パスワード認証を廃止すれば攻撃面そのものが消える。
検知と通知は「気づいて対処を始める」ための仕組みであって、攻撃を止めるものではない。
