# 管理パネル（Admin Panel）

サーバー管理者（Admin）向けの設定 UI。設定ダイアログ内の「管理（Administration）」セクションに表示される。

## アクセス権

- `isAdmin = true` のユーザーのみ表示・操作可能。
- Admin の付与は環境変数 `ADMIN_EMAIL` によるシード（`AdminService.seedAdmin()`、起動時に該当ユーザーを昇格）か、既存 Admin による付与で行う。

## 画面構成

設定ダイアログのサイドバー「管理」セクションに、以下の 4 タブを表示する。

| タブ | コンポーネント | 内容 |
|------|---------------|------|
| ユーザー管理 | `user-management.tsx` | ユーザー一覧・検索・追加・削除、Admin 権限の付与/剥奪、パスワードの再設定・変更 URL の発行（操作は行の ⋮ メニュー内） |
| サーバー設定 | `server-settings.tsx` | 新規登録の許可、サイト名、リンクプレビュー・リッチ埋め込み（既定 OFF） |
| バックアップ | `backup-panel.tsx` | 自動バックアップ設定、手動バックアップ、履歴・ダウンロード・削除 |
| リストア | `restore-panel.tsx` | バックアップ ZIP のアップロードによるシステム復元 |

実装: `frontend/packages/frontend/core/src/desktop/dialogs/setting/admin-setting/`
タブの登録: `index.tsx` の `useAdminSettingList()`
セクション見出し: `setting-sidebar/index.tsx`

## パスワード変更機能

ofuro-wiki のパスワード変更経路は、以下の5つで整理する。
**この表がパスワード変更機能の一覧であり、個別の節はこの表を前提に書かれている。**

| # | 機能 | 対象 | 状態 | 実装 |
|:--:|---|---|:--:|---|
| 1 | **パスワードお忘れですか**（ログイン前・メール） | 本人 | ❌ 未実装（**#116**） | — |
| 2 | **設定画面からのパスワード変更** | 本人 | ✅ | `changeMyPassword` |
| 3 | **パスワードの再設定**（直接変更） | Admin | ✅ | `adminSetUserPassword` |
| 4 | **パスワード変更URL発行 Level1** | Admin | ✅ | `createChangePasswordUrl` |
| 5 | **パスワード変更URL発行 Level2**（SMTP 有効時にメール送信） | Admin | ❌ 未実装（**#132**） | — |

1 と 5 は **v0.1.0 のスコープ外**。

### 前提

ofuro-wiki には**サインアウト状態からのセルフサービスのパスワード再設定が無い**（上表 1 が未実装）。
そのため、パスワードを忘れた利用者の復旧経路は **Admin 経由（3 または 4）のみ**である。
また SSO（#89）で作成されたアカウントは**パスワードを持たない**ため、
SSO を無効化した場合もこの経路が必要になる。

### 2. 設定画面からのパスワード変更（本人）

**設定 → アカウント → パスワードを変更。** 現在のパスワードと新しいパスワードを入力する。

Admin が 3 でパスワードを設定した後、利用者にはこの操作で変更し直してもらう。

> この経路は **PR #130 まで一度も動作していなかった**（`@Public()` と `@CurrentUser()` は
> 併用できず、実行者を特定できていなかった）。resolver を直接呼ぶ単体テストでは
> 検出できないため、E2E で API を通して検証している。

### 3. パスワードの再設定（Admin・直接変更）

ユーザー一覧の行 →「**パスワードの再設定**」。新しいパスワードを入力して設定する。

| 項目 | 内容 |
|------|------|
| 権限 | **Admin のみ** |
| 現在のパスワード | **不要**（忘れているため要求しない） |
| パスワード長 | 8〜128文字 |
| 設定後 | 対象ユーザーの**全セッションを失効**（`tokenVersion` +1） |

全セッションを失効させるのは、アカウントが乗っ取られていた場合に
**攻撃者のセッションを残したまま復旧させない**ため。

> ⚠️ **この操作の後、Admin は「自分が設定したパスワード」を知った状態になる。**
> 以後 Admin は対象利用者として振る舞えるため、4 にはない性質である。
> **本人に URL を渡せる相手であれば 4 を優先すること。**
>
> なお **既存のパスワードを見る手段は Admin にも無い**。パスワードは bcrypt
> （コスト12・ソルト付き）で保存しており、ハッシュから復元できないため、
> できるのは「上書きする」ことだけである。だからこの機能は「確認」ではなく「再設定」。

> ⚠️ **変更を強制する仕組みは入れていない。** 利用者が設定されたパスワードのまま
> 使い続ける可能性がある。**運用として、本人に「サインイン後すぐ 2 の操作で変更する」よう
> 必ず伝えること。** 強制の必要性が出た時点で、強制変更フラグの導入を検討する。

設定操作はサーバーログに記録する（監査ログ #90 の対象）。

### 4. パスワード変更URL発行 Level1（Admin）

ユーザー一覧の行 →「**パスワード変更URL発行**」。

| 項目 | 内容 |
|------|------|
| 発行される URL | `{BASE_URL}/auth/changePassword?token=...` |
| 有効期限 | **24時間** |
| 使用回数 | 1回（使用後にトークンを削除） |
| 権限 | **Admin のみ** |

**URL は画面に表示し、コピーできる。** メール送信に依存しない形にしているのは、
SMTP を設定していない環境（社内利用では珍しくない）でも Admin が
チャット等で手渡しできるようにするため。

3 と違い、**パスワードは利用者本人が決める**ため、Admin は本人のパスワードを知らない。
渡せる相手にはこちらを使う。

> ⚠️ **発行された URL は、それ単体でパスワードを変更できる。**
> 取り扱いはパスワードに準じる（第三者に渡らない経路で送る）。
> 画面上も、閉じると再表示できない旨を明示する。

発行操作はサーバーログに記録する（監査ログ #90 の対象）。

#### 使用済み・期限切れの URL を開いたとき

再設定画面は、**開いた時点でトークンの有効性を確認**し、無効なら入力フォームではなく
「この URL は使用できません」と案内する（`isPasswordTokenValid`）。

確認しない作りだと、無効な URL でも入力フォームが出てしまい、**利用者はパスワードを
入力して送信するまで無効だと気づけない**。実際、開発時の動作確認で繰り返し混乱を招いた。

`isPasswordTokenValid` は**未認証で叩けるが、状態を変えない**（トークンを消費しない）。
`changePassword` を叩けば同じことが分かるため、新たに漏れる情報は無い。
トークンは32バイト乱数のため総当たりは非現実的。
なお**通信に失敗した場合はフォームを表示する**（送信時に改めて検証される）。
ここで「無効」と断定すると、有効な URL を持つ利用者を締め出してしまうため。

#### 有効期限を24時間にしている理由

有効期限は「用途」ではなく**「どう手渡すか」**で決めている。

| 発行元 | 期限 | 理由 |
|---|:--:|---|
| メール送信（`sendPasswordResetEmail` 等） | 1時間 | 利用者がその場で受け取れる |
| **Admin 発行の変更 URL** | **24時間** | チャット等での受け渡しに時間差が生じる |

1時間では、Admin が発行してから利用者が気づくまでに切れてしまい、実運用に耐えない。
**設定可能にはしない**（選択肢を増やすより、既定値を明記する方が運用しやすい）。

実装は `MailService.ADMIN_ISSUED_TOKEN_TTL_MS`。
`password_reset` というトークン種別は**メール送信でも使う**ため、
種別で期限を切り替えるとメール本文の「1時間後に無効になります」と実際の期限がずれる。
そのため呼び出し側が期限を明示する形にしている。

### 5. パスワード変更URL発行 Level2（未実装・#132）

SMTP が有効な場合に、4 の URL を**対象利用者へメールで直接送る**。
Admin が手渡しする手間が消え、平文パスワードや URL がチャットに残らない。

v0.1.0 のスコープ外。

## 国際化（i18n）

- すべての表示文字列は i18n 経由（`useI18n()`）で表示し、ハードコード文字列を持たない。
- キーは `com.affine.admin.*` 名前空間（セクション見出しは `com.affine.settingSidebar.settings.admin`）。
- 汎用語（保存/キャンセル/削除/編集/読み込み中）は既存の共通キー（`Save` / `Cancel` / `Delete` / `Edit` / `Loading`）を再利用する。
- 翻訳定義: `frontend/packages/frontend/i18n/src/resources/en.json`（英語）/ `ja.json`（日本語）。
- キーを追加・変更したら `i18n` パッケージで `yarn build` を実行し、型定義 `i18n.gen.ts` を再生成すること。
- アプリのデフォルト言語は日本語（`modules/i18n/entities/i18n.ts` の既定値 `'ja'`）。

## E2E

`e2e/admin.spec.ts`（バックエンドを `ADMIN_EMAIL=e2e-test@ofuro-wiki.local` で起動して実行）。
Admin API（GraphQL）に加え、Admin パネル UI のラベルがデフォルト言語（日本語）で表示されることを検証する。
パスワード変更機能（#115）については、以下を検証する。

**3. パスワードの再設定（Admin・直接変更）**
- Admin が再設定できること・**Admin 以外は再設定できないこと**
- 再設定したパスワードで**実際にサインインできること**
  （mutation が true を返すだけでは、反映されたか分からない）
- 再設定で**対象ユーザーの既存セッションが失効すること**

**4. パスワード変更URL発行**
- URL を発行できること・**Admin 以外は発行できないこと**
- **トークンが1回で無効になること**、およびエラー名 `INVALID_EMAIL_TOKEN` を返すこと
  （フロントはこれを i18n キーに対応づけて利用者の言語で表示する）
- **使用済みの URL を開くと、入力フォームではなく案内が出ること**

> ⚠️ **別ユーザーとしての確認は、シークレットウィンドウか別ブラウザで行うこと。**
> 認証 Cookie はブラウザプロファイル単位で共有されるため、同じブラウザの別タブで
> サインインすると、元のタブも新しいユーザーに切り替わる（仕様どおりの挙動）。
> E2E が同時に複数ユーザーを扱えるのは `browser.newContext()` で分離しているため。
