# サインインと登録（v0.3.0 M3）

作成: 2026-11-05 / 状態: **決定**（2026-11-06。6 章）

対象: #293（作る前に確認）・#294（root の作成）・#195（招待された未登録の人）・#129（SSO のアカウント切り替え）。
4 件とも「アカウントが無い人がサインインしたとき、作るか」を触るため、1 本の表で決める。

着地（作った後にプライベートを作る）は [`first-workspace.md`](first-workspace.md)、招待の受諾の判定は [`workspace-invitation.md`](workspace-invitation.md)。

---

## 1. 軸

| 軸 | 値 |
|---|---|
| 入口 | パスワード（画面）／パスワード（AI 用 CLI の `login`）／SSO |
| 招待のリンクから来たか | 来た（`/invite/:id` を開いてからサインイン）／来ていない |
| アドレス | root（`ROOT_EMAIL`）／有効なメール招待の宛先／その他 |
| 新規登録（管理画面・`registration_open`） | 開／閉 |
| `AUTH_SIGNIN_AUTOCREATE`（環境変数） | `true`（既定）／`false` |
| SSO の自動作成（管理画面・`oidc_auto_create_user`） | 入／切 |

アカウントがある人は、どの軸でも今と同じ（サインインするだけ）。以下は**アカウントが無い人**だけを扱う。

---

## 2. 今

```
パスワード: POST /api/auth/sign-in（signInOrSignUp）
  ├ 新規登録が開 かつ AUTOCREATE=true → その場で作ってサインイン（確認なし）
  └ それ以外                            → 401 Invalid credentials（誤パスワードと見分けられない。M-2）

SSO: oidc_auto_create_user が入 → 作る。切 → 断る（新規登録の開閉は見ない）
```

- 画面の事前確認（`preflight`）は、M-2 のため常に「登録済み」を返す。画面に新規登録の入口は無い
- root も同じ経路でしか作れない。**閉じた環境では root がサインインできない**（#294）
- 招待された未登録の人は、閉じた環境では参加できない（#195）。招待を受けるにはサインイン済みである必要があるため
- メール招待の URL（`/invite/:id`）は招待メールにしか載らない。**SMTP が無い環境では、本人に届ける手段が無い**

---

## 3. 変えたあと（アカウントが無い人）

| 入口 | アドレス | 作る条件 | 作り方 |
|---|---|---|---|
| パスワード（画面） | その他 | 新規登録が開 かつ AUTOCREATE=true（今と同じ） | **確認してから**作る（4.1・#293） |
| パスワード（画面） | root | **いつでも**（閉でも・`false` でも） | 確認してから作る（4.2・#294） |
| パスワード（画面・招待のリンクから） | 有効なメール招待の宛先 | **いつでも**（閉でも・`false` でも） | 確認してから作り、続けて招待を受ける（4.3・#195） |
| パスワード（CLI `login`） | どれでも | **作らない** | 「ブラウザでアカウントを作ってください」と出す（4.4） |
| SSO | その他 | SSO の自動作成が入（今と同じ） | 今と同じ |
| SSO | root | **いつでも** | 今と同じ（IdP がアドレスを確かめているため確認は要らない） |

作れないときは、今と同じく 401 `Invalid credentials` を返す（誤パスワードと見分けられない）。

## 4. 決め

### 4.1 作る前に確認する（#293）

```
画面: サインイン（メール・パスワード）
  → POST /api/auth/sign-in { email, password }
      ├ アカウントがある              → サインイン（今と同じ）
      ├ 無い・作れる                  → 401 + code: ACCOUNT_NOT_FOUND（作らない）
      │     → 画面:「このメールアドレスは登録されていません。新しいアカウントを作りますか」
      │          [作る] → POST /api/auth/sign-in { email, password, create: true } → 作ってサインイン
      │          [戻る] → 入力に戻る（打ち間違いに気づける）
      └ 無い・作れない                → 401 Invalid credentials（今と同じ）
```

- `create: true` が無い限り、サインインの API はアカウントを作らない
- **存在が分かる範囲は増えない**: 「無い」と分かるのは、作れる環境だけ。そこでは今も、サインインするとアカウントが作られることで分かる
- ⚠️ **ただし、調べる手間は減る。** 今は、無いアドレスを試すたびにアカウントが 1 つでき、IP あたり 1 時間 10 件で止まり、監査ログにも残る。確認を挟むと、作らずに何件でも調べられる。
  そこで `ACCOUNT_NOT_FOUND` を返した回数も、作成と同じ IP あたりの上限（1 時間 10 件）で数える。超えたら 429。未登録への試行の記録（#117 条件 D）も今と同じく残す
- ⚠️ 回数は IP ごとに数える。社内の NAT のように多くの人が 1 つの IP から来ると、全員で 1 時間 10 件になる（アカウントの作成の上限と同じ条件）。リバースプロキシの後ろでは `TRUST_PROXY` の設定が前提
- `AUTH_SIGNIN_AUTOCREATE` の既定は `true` のまま（確認が入るため、打ち間違いでアカウントができることは無くなる）

### 4.2 root は閉じた環境でも作れる（#294）

- 宛先が root なら、新規登録の開閉・`AUTH_SIGNIN_AUTOCREATE`・SSO の自動作成を見ずに作れる。作るときにシステム管理者にする（今と同じ）
- 起動時に root のアカウントがまだ無ければ、ログに警告を出す（`ROOT_EMAIL のユーザーがまだいません。最初にサインインしてください`）
- ⚠️ **root ができるまでの間は、`ROOT_EMAIL` を知っている人なら誰でも、自分のパスワードで root を作れる。** 新規登録が開いている今の既定でも同じ穴がある。閉じた環境では今は塞がっているが、この変更で開く。
  そのため、手順書では「デプロイしたら、最初に root でサインインする」を必ずの手順として書く（6 章の 1）
- ⚠️ **同じ間は、root のアドレスも見分けられる。** 閉じた環境では、root のアドレスだけが「登録されていません」を返す（ほかの未登録は 401）。アドレスを試していけば root のアドレスが分かり、そのまま作れる。root ができれば、どのアドレスでもこの違いは出ない（PR #327 のレビュー）

### 4.3 招待された未登録の人（#195）

- 招待のリンク（`/invite/:id`）を開いてサインインすると、画面は `inviteId` をサインインの API に一緒に送る
- サーバーは、新規登録が閉じていても、次をすべて満たせば作る
  - `inviteId` が**メール招待**であること（招待リンク `__invite_link__` では作らない。リンクを持つ誰でもアカウントを作れてしまい、新規登録を閉じた意味が無くなる）
  - 期限内で、宛先が入力したアドレスと一致すること（大文字小文字は無視。`judgeInvitation` と同じ）
  - 作ったら、画面は招待のページに戻り、今と同じ受諾（`acceptInvite`）で参加する。受諾の判定は `judgeInvitation` 1 か所のまま（サインインの側で受諾を重ねて書かない）。受けたらそのままワークスペースを開く（メール招待は受けると消えるため、招待の情報を取り直すと「期限切れ」と出ていた）
- `inviteId` は UUID（推測できない）で、本人宛てのメールか、招待した人が渡した URL でしか知り得ない。**アドレスだけでは作れない**（メールの到達を確かめる仕組みが無いため、アドレスの一致だけで作ると、招待されたアドレスを知る誰でも本人として入れる）
- ⚠️ **招待の URL を持つ人は、宛先のアドレスでアカウントを作れる。** メールが届いたかを確かめる仕組みが無いため、URL が漏れると、別の人が宛先のアドレスに自分のパスワードを付けて作れる（本人はあとから入れない）。URL は本人にだけ渡す。アカウントの無い人への招待を取り消す画面は無く、7 日で切れる（PR #327 のレビュー）
- プライベートには招待できない（#297）ので、作ったあとに入るのは常に共有。着地でプライベートも作られる（`first-workspace.md`）
- **SMTP が無い環境のために、招待の結果の通知で、アカウントの無い人への招待の URL をコピーできるようにする**（6 章の 2）。メールを送れたときも出す（迷惑メールに入ることがある）。メンバーの一覧には、アカウントの無い人への招待は載らないため、URL を知れるのは招待した直後だけ。見失ったら、もう一度招待すれば新しい URL ができる。通知は URL があるときは自動で閉じない

### 4.4 AI 用 CLI の `login`

- `create: true` を送らない。`ACCOUNT_NOT_FOUND` を受けたら「このアドレスのアカウントがありません。ブラウザでアカウントを作るか、管理者に作ってもらってください」と出して終わる
- 今は CLI の `login` でもアカウントができる。AI 用のアカウントは管理画面で作る手順（`ai-agent-setup.md`）なので、困る人は居ない

### 4.5 SSO でアカウントを選び直せる（#129）

- 認可の要求に `prompt=select_account` を常に付ける（管理画面の設定は作らない）
- Keycloak と Google で、次を確かめてから入れる: アカウントが 1 つでも選ぶ画面が出るか・2 回目以降に選び直せるか・パスワードの再入力を求めないか
- サインアウトで IdP 側もサインアウトさせる話（RP-initiated logout）は含めない

| 確かめること | 種類 |

## 6. 決めたこと（2026-11-06）

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 1 | root ができるまでの穴（4.2） | サインインで作れる。起動時に警告し、手順書に「デプロイしたら最初に root でサインインする」を書く | 今の既定（新規登録が開）と同じ穴で、新しい設定も増えない。`ROOT_PASSWORD` で起動時に作る案は、要望が出たら足す |
| 2 | SMTP が無いときの招待の URL（4.3） | 招待の結果の通知で、アカウントの無い人への招待の URL をコピーできるようにする（メールを送れたときも） | 社内では SMTP が無い環境が普通で、無いと #195 が直らない |
| 3 | SSO で、メール招待の宛先なら自動作成が切でも作るか | 作らない | M3 の範囲を広げない |

## 7. サインインの期限（#332・2026-11-10 決定）

サインインの状態は **30 日** 続く（v0.2.x までは 7 日）。ブラウザも AI 用 CLI も同じ。

| 所 | 値 |
|---|---|
| トークン（JWT）の `exp` | 発行から 30 日 |
| クッキー（`affine_token`・`affine_csrf_token`）の `maxAge` | 30 日 |

- 2 つは 1 つの定数（`SESSION_TTL_DAYS`）から作る。片方だけ変えると、クッキーが残っているのにトークンが切れている（またはその逆）状態になる
- `.env` では変えない（ユーザー決定。14 日・`.env` で変える案も検討して採らなかった）
- 受け入れるリスク: 漏れたトークンが使える期間が 30 日に延びる。1 本ずつ取り消す手段は無く、止めるには全端末のサインアウトかパスワードの変更。本来の解決は #269（個人用アクセストークン）
- 反映より前に発行されたトークンは 7 日のまま切れる。次のサインインから 30 日
- 招待の期限（7 日）は別物で、変えない
