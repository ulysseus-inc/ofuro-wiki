## 0. 用語（2026-10-26 決定）

管理者は 2 種類ある。今の画面はどちらも「管理者」と出しており混乱するため、**呼び分ける**。

| 種類 | 呼び名 | 誰 | 範囲 |
|---|---|---|---|
| システム | **root** | `.env` の `ROOT_EMAIL`（1 人） | サーバー全体。消せない、外せない |
| システム | **システム管理者** | root が追加した人 | サーバー全体。すべての共有ワークスペース |
| ワークスペース | **ワークスペース管理者** | システム管理者が選んだ一般ユーザー | その共有ワークスペースの招待・役割・設定 |
| ワークスペース | **メンバー** | 招待された人 | 読み書き |
| ワークスペース | **閲覧者** | 招待された人 | 読むだけ |

- 本文の「admin」はシステム管理者を指す（root を含むときは「root・admin」と書く）
- 今の役割の「オーナー」は、共有ワークスペースでは使わない。プライベートでは本人がオーナー
- 画面の「管理者」（ユーザー一覧のバッジ、ワークスペースの役割）は、上の呼び名に分けて直す。`CLAUDE.md` のロール体系の表も直す

## 1. なぜ見直すか

今の仕組みは「ユーザーごとに、最初のサインインでワークスペースが 1 つ自動で作られる」だけで、
2 つ目を作る入り口は隠してある（2026-02-14 b86ad18。意図は「**最低 1 つ**」だった）。その結果、

| 困りごと | 中身 |
|---|---|
| 共有の場を増やせない | 部署・プロジェクトごとに共有のワークスペースを分けられない |
| 個人の場が無くなる | 社内 Wiki に使ったワークスペースの持ち主（管理者など）には、個人用が残らない |
| 共有の場が個人に紐づく | 共有している社内 Wiki が、ある一般ユーザーの持ち物になっている |
| **消えると戻らない** | そのユーザーを消すと、共有の社内 Wiki が**メンバーごと消える**（#296） |
| 抜け道 | クイック検索（Ctrl+K）の「新規ワークスペース」と、ワークスペースの取り込み API（`POST /api/workspaces/import`、サインインしていれば誰でも）からは作れてしまう |

根にあるのは、**共有の場が「誰か 1 人の持ち物」になっている**こと。持ち主が居なくなると迷子になる。

## 2. 考え方

**ワークスペースを 2 種類に分け、共有の場は組織（管理者）の持ち物にする。**

```
                ┌──────────────────────────────┐
  ユーザー A ──▶ │ A のプライベート（A だけ）    │
                └──────────────────────────────┘
                ┌──────────────────────────────┐
  ユーザー B ──▶ │ B のプライベート（B だけ）    │
                └──────────────────────────────┘
                ┌──────────────────────────────┐
  A・B・C  ───▶ │ 共有「社内Wiki」              │ ◀── root・admin が
                ├──────────────────────────────┤      必ず管理できる
  B・C     ───▶ │ 共有「営業部」                │
                └──────────────────────────────┘
```

## 3. 決定（2026-10-26 の議論）

### 3.1 2 種類のワークスペース

| | プライベート | 共有 |
|---|---|---|
| 数 | **各ユーザーに 1 つ**（最初のサインインで自動で作る） | いくつでも |
| 作る人 | システム | **root・admin だけ** |
| 入れる人 | **本人だけ**（招待できない） | 招待された人 |
| 管理する人 | 本人 | **root・admin 全員** ＋ admin が選んだ一般ユーザー |
| ユーザーを消したとき | その人のプライベートだけ消える | 消えない |

### 3.2 管理者

| 呼び名 | 誰 | できること |
|---|---|---|
| **root** | `.env` の `ROOT_EMAIL` のユーザー。**システムで 1 人** | admin と同じ。加えて、**削除も管理者外しもできない** |
| **admin** | root（または admin）が管理者にしたユーザー | **全員が同じ権限。** サーバーの管理と、**すべての共有ワークスペースの管理** |
| 共有ワークスペースの管理者 | admin が選んだ一般ユーザー | 選ばれた共有ワークスペースのメンバー・設定の管理。**作成・削除・管理者の任命はできない** |

- **すべての共有ワークスペースに、root が必ず居る。** admin が 1 人も居なくても、迷子の共有ワークスペースは生まれない
- root と admin は**管理のためのアカウント**で、普段の利用には使わない（3.3）

- admin の共有ワークスペースへの権限は、メンバーとして登録するのではなく **admin という立場から出す**。
  admin が入れ替わっても、管理できる人が居なくなる共有ワークスペースは生まれない
- ルート管理者は、`.env` を書き換えることで引き継ぐ。**最後の管理者を守る仕組みは、ルート管理者だけで足りる**
  （「最後の 1 人」を数える処理は作らない）
- 手順書では、`ROOT_EMAIL` を**個人ではなく管理専用のアカウント**（例: `wiki-admin@…`）にすることを勧める（3.3）

### 3.3 root・admin は共有ワークスペースの中身をすべて見られる

製品の約束は「**権限の無い人には、存在ごと見せない**」。root・admin は**管理のための特別なアカウント**で、
普段の利用者ではない。したがって、root・admin が全部見えることは、この約束と矛盾しない。

- ページ単位の権限で隠したページも、root・admin には見える（**統制を優先**）
- 今も、サーバー Admin はドキュメントの権限を素通りする（`permission.service.ts` の「① バイパス」）。それを仕様として認める
- 手順書では、**root・admin は管理専用のアカウントにし、普段は一般ユーザーのアカウントを使う**よう案内する
- **プライベートは本人だけの場とする。** root・admin にも、画面からプライベートを開く道は作らない。
  障害の調査・修正で DB やバックアップを扱うときに見えてしまうことはある、という扱い。
  ⚠️ 今の「① バイパス」はプライベートにも効く（URL を知っていれば開ける）。**素通りは共有ワークスペースに限る**

### 3.4 ページの移動は作らない。代わりにワークスペースのバックアップを管理機能にする

プライベートから共有へページを移す機能は作らない。1 件ずつなら、書き出し（Markdown 等）と取り込み、またはコピーで行う。

ワークスペース単位の書き出し・取り込みは、**API としては既にある**（`backup.controller.ts`）。これを管理機能として整える。

| | 今 | 新しい仕組み |
|---|---|---|
| 書き出し `GET /api/workspaces/:id/export`（zip、全ページ） | 持ち主だけ。画面なし | 共有: admin と共有ワークスペースの管理者。プライベート: 本人 |
| 取り込み `POST /api/workspaces/import`（zip → **新しいワークスペース**） | サインインしていれば誰でも | **admin だけ**（取り込みは共有ワークスペースの作成にあたる） |

画面は**ワークスペースの設定**に置く。

### 3.5 保護

| 保護 | 中身 |
|---|---|
| ルート管理者 | 画面から削除・管理者外しができない（今は外せるが、再起動で戻る紛らわしい状態） |
| 自分自身 | 自分は削除できない（優先度は低い） |
| 共有ワークスペース | root・admin の権限は外せない（3.2 のとおり立場から出るため、外す操作そのものが無い） |

## 6. 今のデータの移し方（一回限りの移行ツール）

恒久的な機能にはしない。新しい仕組みを入れる版で、**移行ツールを一度だけ流す**。
ページは動かさず、ワークスペースの種類と管理者だけを書き換える（中身が崩れない）。

| 今のワークスペース | 移行後 |
|---|---|
| ほかのメンバーが居る | **共有**。持ち主は外し、root・admin の管理に入れる。元の持ち主はメンバー（または共有ワークスペースの管理者）として残す |

| 1 人が「本人だけ」のものを 2 つ以上持つ | 移す前に一覧を出し、人が決める（共有にする／1 つにまとめる） |
| マニュアル専用（`ffffffff-…`） | 対象外。今のまま |

対象は、社内本番・ENIGMA 環境・公開デモ。まず手元の複製で流して確かめる。

## 11. 方式の比較と判定（2026-10-26）

| | A. 本仕様（プライベートと共有） | B. オーナー案の拡張 |
|---|---|---|
| 考え方 | 共有は組織の持ち物。root が必ず居る | どのワークスペースにも持ち主が居る。全員が作れる |
| 迷子にならない | ◎ 仕組みの上で起きない | ○ 持ち主を消すときに譲る処理に漏れがあると起きる |
| 統制 | ◎ 共有はすべて admin の管理下 | △ 増えるのを止められず、一覧を別に作る |
| 使う人の自由 | △ 共有は admin に頼んで作る | ◎ 誰でも作れる |
| 個人の場 | ◎ 全員に必ず 1 つ | △ 共有に使った人には残らない（今の問題） |
| 作る量 | △ 役割・権限の作り直し | ◎ 少ない |

**判定: 製品の仕様は A。作りは B のデータの形を使う。**

社内 Wiki で大事なのは「消えない」「管理者が把握できる」ことで、誰でも作れる自由より優先する。
社内本番で、社内 Wiki が一般ユーザーの持ち物になっていたことが、B の弱点を実際に示している。

A の弱点は作る量。今の作りはオーナーに強く依存している（バックエンド約 40 か所、フロントエンド約 100 か所。多くは AFFiNE 由来）。そこで、

- **共有ワークスペースの持ち主（`ownerId`）は、データの上では root にする。** 画面では「root」と出し、譲れないようにする
- プライベートの持ち主は本人のまま
- システム管理者の権限は、今の「① バイパス」を共有ワークスペースに限って出す

こうすれば、データの形とオーナーの仕組み（スキーマ・`ownerId` の参照・フロントの Owner 判定）は今のまま使える。
root は消せないので、持ち主が居なくなることも無い。root を `.env` で別の人に替えたときは、
共有ワークスペースの `ownerId` を新しい root に付け替える（起動時の処理。12.7 で設計した）。

## 12. 実装の設計（2026-10-27）

11 章の判定どおり、**データの形は今のまま使い、ワークスペースに「種類」を 1 つ足す**。
調べた今の作り（2026-10-27）と、変える所をまとめる。

### 12.1 データ

| 所 | 今 | 変える |
|---|---|---|
| `workspaces.kind` | 無い | 追加。`'private'` / `'shared'`。既定は `'private'`（マイグレーションで足す。分類は 12.9 の移行ツール） |
| `workspaces.owner_id` | 作った人 | プライベート: 本人。**共有: root**（12.7） |
| `workspace_members.role` | `owner` / `admin` / `member` / `reader` | 意味だけ変える。共有の `owner` は root、`admin` は**ワークスペース管理者** |
| `users.is_admin` | サーバー全体の Admin | システム管理者（root を含む） |

- root は `ROOT_EMAIL` のユーザー。DB に印は持たない（`.env` が正。`isAdminEmail` で判定する。12.1.1）
- **root は共有ごとに `owner` のメンバーの行を持つ**（作成時と 12.7 で作る）。root 以外のシステム管理者は行を持たず、立場から素通りする（3.2）
- マニュアル（`ffffffff-…`）は `kind = 'shared'` にする。書けないのは今の `isManualWorkspace` の判定が先に効くため変わらない

#### 12.1.1 root の設定 `ROOT_EMAIL`（2026-11-05 改名）

v0.2 までの名前は `ADMIN_EMAIL`。システム管理者は何人でも置けるため、「システム管理者のアドレス」と読み違えられる。v0.3.0 で `ROOT_EMAIL` に改める。

古い名前で動いているサーバーは、更新しただけで root が居なくなってはいけない（root の保護と共有の持ち主が、黙って外れる）。当面は古い名前も読む。

| `ROOT_EMAIL` | `ADMIN_EMAIL` | 動き |
|---|---|---|
| あり | なし | `ROOT_EMAIL` を使う |
| なし | あり | `ADMIN_EMAIL` を使う。起動ログに改名を促す警告 |
| あり | あり（同じ値） | `ROOT_EMAIL` を使う。起動ログに `ADMIN_EMAIL` を消すよう警告 |
| あり | あり（違う値） | **起動しない**（どちらが root か決められない） |
| なし | なし | root なし（今と同じ） |

- 空白だけの値は「なし」と同じ。値の比較は前後の空白を除いてから（v0.2 の `ADMIN_EMAIL` と同じ）
- `docker-compose.yml` は両方をコンテナに渡す（古い名前の `.env` でも上の表どおりに動くように）
- `ADMIN_EMAIL` を読むのは 1.0.0 まで。v0.3.0 のリリースノートに改名を書く
- 判定の関数名（`getAdminEmail` / `isAdminEmail`）は変えない（#320 で揃える）

### 12.2 システム管理者の素通りを、共有に限る（3.3）

今は 3 か所が、`is_admin` なら**どのワークスペースでも**通している。プライベートも通るので、3 か所とも `kind = 'shared'` のときだけにする。

| 所 | 今 |
|---|---|
| `WorkspaceMemberGuard`（GraphQL・REST の入口） | `isAdmin` なら全部通す |
| `PermissionService.getDocRole`（ページの権限・① バイパス） | `isAdmin` なら `Owner` |
| `SyncGateway.checkWorkspaceAccess`（同期） | `isAdmin` なら全部通す |

規則は `common/workspace-kind.ts` の `systemAdminBypasses(isAdmin, kind)` 1 か所に置き、3 か所から呼ぶ（判定を散らさない）。
⚠️ **拒否が既定。** 素通りするのは `kind` が `'shared'` のときだけで、NULL や未知の値は素通りさせない。

`is_admin` を見る所はほかに無いか、実装時（2026-10-27）に全体を検索して確かめた。
⚠️ `isAdmin` の文字だけで探すと、包んだ関数（`PermissionService.isServerAdmin`）を経由する所を見落とす。
実際に、一覧と検索の絞り込みの 2 か所を最初は見落とし、E2E で見つけた。

| 所 | 用途 | ワークスペースの中身に届くか |
|---|---|---|
| 上の 3 か所 | 素通り | 届く → 共有だけにした |
| `PermissionService.filterReadable`（一覧の絞り込み） | Admin は全件 | 届く → 共有だけにした |
| `PermissionService.readableDocFilter`（検索の絞り込み） | Admin は全件 | 届く → 共有だけにした |
| `PermissionService.getDocRole` のマニュアルの分岐 | Admin はマニュアルを読める | マニュアルだけ（共有） |
| `AdminGuard` | 管理画面の API | 届かない（サーバーの管理） |
| `user.resolver`（`features`） | 画面に管理の項目を出す | 届かない |
| `intrusion-detection` | 不審なサインインを管理者に知らせる | 届かない |
| `backup.controller`（書き出し） | 12.6 | 共有だけ（種類を先に見る） |
| `workspace.service`（作成・削除） | 12.3・12.5 | 共有だけ |

画像・検索・コメントなどの API は、入口のガード（`WorkspaceMemberGuard`）とページの権限（`PermissionService`）を通る。

逆向きの漏れ（**メンバーの行だけを見て、素通りの管理者を断る所**）もある。
画像を読む API（`blob.controller` の GET）は、ガードの後でメンバーの役割を自分で確かめており、
メンバーの行を持たないシステム管理者を断っていた（E2E で発見）。`WorkspaceService.effectiveRole` で判定する。
コメントの削除・解決（`comment.service`）も役割を直接見るが、コメントは使っていない機能のため、今回は変えない。

### 12.3 作る

**共有も、画面から作る。** API だけで作ったワークスペースは中身（ルート文書）が空で、画面で開けない（「ワークスペースを読み込めませんでした」）。
最初のサインインと同じく、画面がワークスペースを作ってテンプレートを入れる流れを使う。

| 経路 | 今 | 変える |
|---|---|---|
| `createWorkspace`（GraphQL） | 誰でも何個でも | 引数 `kind` を足す。`private`: **プライベートをまだ持たない人だけ**。`shared`: **システム管理者だけ**。持ち主は root（12.7） |
| 最初のサインイン（`first-workspace.md`） | `createWorkspace`。**マニュアル以外のワークスペースが 1 つも無い**ときだけ作る | `kind: private` で呼ぶ。作る条件を「**自分のプライベートが無い**」に変える（12.3.1） |
| Ctrl+K「新規ワークスペース」・作成のダイアログ | 誰でも | システム管理者にだけ出す。`kind: shared` で作る。「ワークスペースのタイプ」の欄は出さず、作り先は常に ofuro-wiki（「ローカルストレージ」を選ぶと、サーバーに保存されないブラウザだけのワークスペースができ、`kind` も効かないため。ローカルの仕組みのコードは残す）。サーバーの情報が揃うまで「作成」は押せない（揃う前に押すとローカルに作られるため） |
| 取り込み `POST /api/workspaces/import` | サインインしていれば誰でも | **システム管理者だけ**。共有として作る（本人がプライベートを取り込んで戻す手段は、意図して作らない） |

#### 12.3.1 着地でプライベートを作る条件（2026-10-28）

今の画面は「マニュアル以外のワークスペースが 1 つも無い」ときにしかプライベートを作らない。
共有に入っている人（システム管理者は全員、一覧に共有が載る）は、プライベートが無くても作られない。
本番の複製で、移行後に 2 人がこの状態になった（社内 Wiki の元の持ち主と、メンバーだけの人）。

- 画面のワークスペースの一覧（`WorkspaceMetadata`）は ID しか持たず、種類や持ち主を足すと AFFiNE 由来の仕組みに広く手が入る
- そこで、GraphQL に `myPrivateWorkspaceId`（自分が持ち主のプライベートの ID。無ければ null）を足し、着地はこれで決める

```
着地（/）
  ├ myPrivateWorkspaceId が null → プライベートを作る（kind: private）
  └ ある                          → 前回のワークスペース（無ければ自分のプライベート）を開く
```

⚠️ 一覧の読み込みの前に作り始めないこと（今の着地も、一覧の読み込みを待ってから判断している）。

- 開く先が一覧にまだ無い（別のタブで作った直後など）ときは、移動せずに一覧の更新を待つ
- 作るのに失敗したら、次に一覧が変わったときに作り直せるようにする（白い画面で止めない）

制約:
- **root（`ROOT_EMAIL` のユーザー）がまだサインインしていない間は、共有を作れない**（持ち主が決まらないため断る）
- **1 人 1 つ**はアプリの判定と、DB の部分一意インデックス（`kind = 'private'` の `owner_id`）の両方で守る。
  最初のサインインの同時の要求（複数のタブなど）で 2 つ作ろうとしても、2 つ目は DB が断る。
  インデックスは移行ツールの PR（12.12 の 2）で入れた。重複が残っている DB では作られず、移行ツールが作る（12.9）

### 12.4 招待・役割

| 所 | 今 | 変える |
|---|---|---|
| 招待（`inviteMembers`・招待リンク・受諾） | 種類を見ない | **プライベートでは断る**（サーバーで断り、画面にも出さない） |

### 12.7 root が替わったとき

起動時（今の `seedAdmin` の後）に、共有ワークスペースの持ち主を今の root に付け替える。

```
ROOT_EMAIL のユーザーが居る
  └ 持ち主が root でない共有ワークスペースごとに
       owner_id ← root
       root のメンバーの行を owner にする（無ければ作る）
       前の root の行は admin（ワークスペース管理者）に下げる … ⚠️ 消さない。消すとその人が読めなくなる
```

`ROOT_EMAIL` のユーザーがまだ居ない（最初のサインインの前）ときは、何もしない。共有は作れない（12.3 で断る）。

⚠️ **マニュアルは付け替えない。** マニュアルは共有だが、持ち主はシステムのアカウントのまま。付け替えると、シードが古いマニュアルを持ち主で探せず作り直しに失敗し、一覧への自動参加も止まる（実装中に開発環境で発生。E2E はマニュアルの無い環境とみなしてスキップし、失敗として出なかった）。

- **前の root は、システム管理者のまま残る**（`is_admin` は外さない）。すべての共有を見られる立場が続くので、要らなければ管理画面で管理者を外す
- `ROOT_EMAIL` の打ち間違いで、意図しない人がすべての共有の持ち主になりうる。**付け替えた件数とワークスペースを、起動ログと監査ログに残す**（後から気付けるように）

|---|---|

| 今のワークスペース | 「ワークスペース」の各項目の見出しの下に出す。サイドバーの見出しは狭いため使わない。見出しの無い「メンバー」は先頭に出す |

「︙」の項目は [`workspace-member-roles.md`](workspace-member-roles.md) 3 章。

### 12.9 移行ツール（一回限り・6 章）

`backend/src/scripts/migrate-workspace-kind.ts`。`purge:index` と同じ作り。

- **既定は下見**（書き換えずに、分類の一覧を出す）。`--apply` で書き換える
- **何度流しても同じ結果**（冪等）。途中で止まっても、もう一度流せばよい
- 戻し方は「流す直前のバックアップからリストア」。Release ノートにも書く

| 分類 | 条件 | 書き換え |
|---|---|---|
| 共有 | 持ち主のほかに、参加済みのメンバーが居る | `kind = 'shared'`、12.7 と同じ付け替え（元の持ち主は `admin` に） |
| プライベート | 持ち主だけ | そのまま（`kind` は既定の `'private'`） |
| 要判断 | 1 人が「持ち主だけ」のものを 2 つ以上持つ | 書き換えない。一覧を出し、人が決める（共有にする／残す） |
| 対象外 | マニュアル | `kind = 'shared'` のみ（マイグレーションで済み） |
| 済み | すでに `kind = 'shared'` | 何もしない（2 回目以降に流したとき） |

実装の細部（2026-10-28 決定）:

```
npm run migrate:workspace-kind:prod                       # 下見（何も書き換えない）
npm run migrate:workspace-kind:prod -- --apply            # 書き換える
npm run migrate:workspace-kind:prod -- --apply --share <ID>,<ID>   # 要判断のうち、共有にするもの
```

- 判断は `WorkspaceMigrationService` に置き、スクリプトは薄くする（`purge:index` と同じ）
- 共有にするときは、種類を `'shared'` にしてから `AdminService.reassignSharedOwner` で持ち主を root に付け替える
  （12.7 と同じ処理を使う。元の持ち主はワークスペース管理者になり、付け替えは監査ログに残る）
- 種類を変えたことも監査ログ（`workspace.kind.migrate`）に残す
- **root（`ROOT_EMAIL` のユーザー）が居なければ、何も書き換えずに止める**（共有の持ち主が決まらない）
- 要判断で残したものは、`--share` で共有にするか、書き出し・取り込み・削除で 1 つにまとめる（ツールではまとめない）
- `--share` に渡せるのは、プライベートか要判断になるもの。打ち間違い・マニュアル・もともと共有になるものを渡すと、何も書き換えずに止まる（下見でも警告する）。**すでに共有のもの（済み）は渡してよい**（何もしない。途中で失敗したあと、同じ引数で流し直すため）
- **途中で失敗したら、そのまま流し直す。** 共有にしたものは次から「済み」になり、持ち主の付け替えは毎回すべての共有を見直すため、流し直せば揃う
  （監査ログ `workspace.kind.migrate` は種類を変える**前**に書く。落ちても欠けず、流し直したときに重複しうるだけ）
  （そのため監査ログは「共有にしようとした」記録であり、実際の種類は `workspaces.kind` を正とする。監査ログを書けなければ種類は変えない）
- **招待中（未承諾）の人は、参加者に数えない。** 招待は別の表（`invitations`）にあり、まだメンバーではない。持ち主だけのものはプライベートになり、その招待は受けられなくなる（`assertInvitable`）
- 一意インデックスを作る間は `workspaces` への書き込みが止まる（`CONCURRENTLY` でない）。表は小さい（本番で 5 件）ので一瞬だが、利用の少ない時間に流す

| 下見 | 5 件: 共有にする 1（社内 Wiki・ほかの参加者 4 人）／プライベート 3／要判断 0／マニュアル 1 |
| `--apply` | 社内 Wiki が共有になり、持ち主が root、元の持ち主がワークスペース管理者。ほかのメンバーの役割は変わらない |
| 2 回目 | 「済み 1」で何も書き換えない |
| 監査ログ | `workspace.kind.migrate` と `workspace.owner.reassign` が 1 件ずつ |
| 1 人 1 つ | 重複が無く、マイグレーションの段階で一意インデックスが作られた |
| 画面 | 元の持ち主は社内 Wiki で招待できる。root はプライベートを URL で開くと「アクセス権がない」 |

- ⚠️ **持ち主だけのワークスペースを持たない人**（本番では 2 人。社内 Wiki の元の持ち主と、メンバーだけの人）は、移行後もプライベートが無い。画面が「マニュアル以外のワークスペースが 1 つも無い」ときしか作らないため。画面の PR で直す（`release-plan-v0.3.0.md` M2）
- ⚠️ バックアップを別の DB に戻して試すときは、`backup_records` の表が無い（リストアでバックアップの一覧を巻き戻さないため、バックアップに含めていない）。起動に要るので、`20260215000000_add_backup_records` の SQL で作る

#### 1 人 1 つを DB で強制する（12.3 の部分一意インデックス）

`workspaces(owner_id) WHERE kind = 'private'` の一意インデックス `workspaces_one_private_per_owner`。

- **マイグレーションは「重複が無ければ作る」。** 重複があると作れず、ふつうに `CREATE` すると起動時のマイグレーションで失敗して止まるため
  （移行前の既存データは、全部が `'private'` で、1 人が 2 つ以上持つことがある）
- 重複があって作れなかった環境は、移行ツールが `--apply` の最後に作る（要判断が残っていれば作らず、残っている件数を出す）
- マニュアルは、種類を足したマイグレーションで `'shared'` にしており、作り直すときも共有で作る。この重複の検査（`kind = 'private'`）には入らない
- ⚠️ **次に `prisma migrate dev` でマイグレーションを作ったら、`workspaces_one_private_per_owner` を消す `DROP INDEX` が混ざっていないか確かめる。** 部分一意インデックスは `schema.prisma` に書けず、Prisma が「スキーマに無いインデックス」として消そうとすることがある
- 作った後は、同時の要求で 2 つ目を作ろうとしても DB が断る。`createWorkspace` はこれを「すでにある」として扱う
  （この一意インデックスの違反のときだけ。Prisma 7 は `meta.target` を返さず、制約の名前は `meta.driverAdapterError.cause.originalMessage` に入る。ほかの一意制約の違反は、原因を隠さないようそのまま投げる）

### 12.10 AI エージェント用 CLI

CLI は一覧（`workspaces`）に載ったワークスペースを扱う。システム管理者のアカウントで使うと、12.8 のとおり**共有をすべて扱える**。
root・admin は管理用で、AI 用のアカウントを管理者にしない、と手順書で案内している（変えない）。プライベートへの書き込みは、本人のアカウントなら今と同じ。

### 12.13 ワークスペース名（#319・2026-11-11 決定）

ワークスペース名は 2 か所にある。**正はワークスペースの中（ルート文書の `meta.name`）**。

| 所 | 中身 |
|---|---|
| ルート文書の `meta.name`（Yjs） | 画面で付けた・変えた名前。サイドバーと管理画面の一覧はここを出す |
| `workspaces.name`（DB） | 作った時に一度だけ書かれる。以後は変わらず、ほぼ `ofuro-wiki` のまま |

**名前が要る所では、ルート文書から読み、読めなければ DB の値を使う**（`IndexReaderService.workspaceName`）。
DB の `workspaces.name` は書き換えない（2026-11-11 決定）。

| 使う所 | 中身 |
|---|---|
| ワークスペース削除の監査ログ（`targetName`） | 消す**前**に読む |
| 招待メール | |
| 招待の情報（招待リンク・メールの URL を開いたときの表示） | |
| 通知（画面・メール）のワークスペース名 | |
| 移行ツールの下見の一覧と、監査ログ（`workspace.kind.migrate`） | |
| ユーザー削除の確認に出すプライベートの名前（12.8.3） | 実装済み |
| 管理画面「ワークスペース」の一覧（12.8.1） | 実装済み（画面がルート文書から読む） |
| ワークスペースの書き出し（ファイル名と、ZIP の中の名前） | 取り込むと「<名前> (imported)」になる。v0.3.0 の手順書の確認で、DB の値（`ofuro-wiki`）のままだったのが見つかった（2026-11-11） |

- DB を書き換える案（名前を変えたら DB も更新し、今ある分は移行で写す）は採らない。名前は同期で届くため、どの経路の変更も拾うには同期の処理に手を入れることになり、
  失敗すると食い違う。読み直せば食い違わず、移行も要らない
- 読むたびにルート文書を組み立てる。使うのは招待・削除・通知のときだけなので、手間は問題にしない

### 12.12 作る順番（PR の分け方）

| # | 中身 | 理由 |
|---|---|---|
| 1 | データ（`kind`）・判定（12.2）・作成と招待の制限（12.3・12.4）・削除（12.5）・root の付け替え（12.7） | 権限の芯。ここだけで #296 が直る |
