# バックアップとリストア

**サーバー全体のバックアップ（`pg_dump` + ブロブ）と、そこからの復元。**
管理画面の「バックアップ」「リストア」から使う。#212（2026-09-11 設計）。

> ワークスペース単位のエクスポート／インポート（`.ofuro-backup.zip`）は別物。
> この文書は Admin によるサーバー全体のバックアップだけを扱う。

---

## 1. ⚠️ バックアップの作成は非同期ジョブ（#212）

### 何が起きていたか

作成は**1つのリクエストの中で**、`pg_dump` → ブロブのコピー → ZIP → DB 記録を行い、
終わるまで応答しなかった。データが増えて約27秒かかるようになり、

| 壁 | 時間 | 結果 |
|---|---|---|
| ブラウザの既定のタイムアウト（`fetch.ts`） | 15秒 | 画面は「失敗」。**サーバーは成功している** |
| 本番の nginx（`location /` の `proxy_read_timeout`） | 60秒 | 504（2026-09-11 本番の設定を読んで確認） |

⚠️ **タイマーを延ばすだけでは足りない。** 60秒の壁はブラウザ側では越えられない。

### 流れ

```
作成ボタン → adminCreateBackup
   ├ 別のジョブ（バックアップ／リストア）が動いていれば拒否   ← 3章
   ├ status: running の記録を先に作る
   └ すぐに返す                                             ← 15秒・60秒の壁に当たらない
        ↓ 裏で pg_dump → ブロブのコピー → ZIP
   完了: running → completed（ファイル名・サイズ・件数を書く）
   失敗: running → failed（作りかけのファイルは片付ける）

画面: 一覧に「実行中」と出し、running がある間だけ一覧を取り直す
```

⚠️ **戻り値の約束が変わった。** `adminCreateBackup` は `status: 'running'` を返す
（以前は `completed`）。完了を知りたい側は一覧を取り直して待つ。

### 状態

| `status` | 意味 |
|---|---|
| `running` | 作成中。ZIP はまだ無い（サイズ・件数は 0） |
| `completed` | 作成済み。ダウンロード・リストアに使える |
| `failed` | 作成に失敗した。ZIP は無い |

`BackupRecord.status` は `VarChar(50)`・既定 `'completed'` なので、状態を足すのに
**スキーマの移行は要らない**。

## 2. ⚠️ 実行中は削除を拒否する（2026-09-11 決定）

`running` の記録を消そうとしたら拒否する（`BACKUP_IN_PROGRESS`）。

⚠️ **拒否しないと壊れる。** 削除は ZIP が無くても記録を消せるため、

```
running の記録を削除 → 記録は消える
        ↓ ジョブは走り続ける
最後に「completed に更新」しようとして、消えた記録に当たって失敗
        ↓
⚠️ ZIP だけが残る（どこからも見えないファイル）
```

保存期間を過ぎた古いバックアップの自動削除（`pruneOldBackups`）も、`running` は対象にしない。

---

## 3. ⚠️ バックアップとリストアは同時に1つだけ（2026-09-11 決定）

**バックアップとリストアで1つの鍵を共有する。** どちらかが動いている間は、もう片方も、
同じ種類の2本目も拒否する（`BACKUP_IN_PROGRESS`）。

| 重なり | 何が起きるか |
|---|---|
| バックアップ中にリストア | `pg_dump` が書き換え途中の DB を読む。**どちらの結果も信用できない** |
| バックアップ2本 | 以前は画面が「失敗」と出て押し直すと、裏で前の `pg_dump` が走ったまま2本目が始まった |
| 手動と定期実行（毎日3時） | 同じ処理を呼んでいる。定期実行も鍵を取り、取れなければその回は見送る |

⚠️ **鍵はメモリ上に持つ。** バックエンドが**1プロセスで動いていること**が前提
（#151 の変更通知と同じ前提）。複数インスタンスに増やすときは DB の鍵に置き換えること。

### 再起動したとき

実行中に落ちると `running` のまま残る。**起動時に `running` を `failed` にする**
（プロセスが無い以上、その作業は二度と終わらない）。

---

## 3b. ⚠️ バックアップ一覧は「ディスク上の ZIP の目録」（2026-09-11 決定）

**`backup_records` は業務データではなく、ディスク上のバックアップ ZIP を管理する目録である。**
したがって**復元しても巻き戻さない**。

| | 復元で |
|---|---|
| 業務データ（ワークスペース・ページ・ブロブ など） | バックアップ取得時点に戻す |
| **`backup_records`（バックアップの一覧）** | **戻さない**（いまディスクにある ZIP を指し続ける） |
| ディスク上の ZIP | そのまま |

実装: `pg_dump --exclude-table=public.backup_records`。表そのものがダンプに入らないので、
`pg_restore --clean` も触らない（表はマイグレーションで作られる）。

### なぜ外すのか

外していなかったころ、復元は `pg_restore --clean --if-exists` で**一覧も取得時点に巻き戻していた**。

| | 何が起きたか |
|---|---|
| 同期のころ | 記録は ZIP を作ったあとに書くので、**ダンプに自分の記録が無い**。復元すると使ったバックアップの記録が**消え、ZIP だけが残る**（開発環境で ZIP 18個に対し記録 3件・約1.9GB の迷子を確認） |
| 非同期（#212） | 記録は先に `running` で書くので、**ダンプに `running` の自分の記録が入る**。復元すると**`running` に巻き戻り**、実行中は削除を拒否するため**消せない** |

⚠️ どちらも「一覧が DB の状態の一部として巻き戻る」ことが原因。目録として扱えば両方消える。

---

## 4. リストア

`POST /api/backup/admin/restore`（ZIP のアップロード）。同期で行う。

- 3章の鍵を取る（バックアップ中なら拒否）
- ⚠️ バックアップの一覧（`backup_records`）は巻き戻らない（3b章）
- 実行中は同期（Socket.IO）を止める（`enterRestoreMode`）

⚠️ リストアは今も**同期処理**で、大きなバックアップでは同じ60秒の壁に当たり得る。
本件（#212）の範囲外。
