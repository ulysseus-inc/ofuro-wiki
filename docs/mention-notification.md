# メンションと通知

エディタで `@` からメンバーを選ぶと、本文にメンションが入り、相手に通知が届く。

---

## 1. 流れ

```
@ → メンバーを選ぶ（at-menu-config/services/index.ts）
   ├ 本文に挿入: ' '（1文字）+ 属性 mention: { member: <相手の id> }
   └ mentionUser（GraphQL）→ バックエンドが相手に Mention 通知を作る
        戻り値: Boolean!（true）
```

- 自分をメンションしたときは通知を作らない（`mentionUser` が何もせず `true` を返す）
- 相手がページを読めないときは `MENTION_USER_DOC_ACCESS_DENIED` になり、画面で知らせる
  （「このメンバーはこのドキュメントへのアクセス権がなく、通知されません。」）

### メンションできる相手（#223）

メンションは、**同じワークスペースのメンバーで、そのページを読める人**の間だけの機能。
「このページを見て」と知らせるものなので、ページを読めない人に送っても意味がなく、
通知のタイトルから**読めないページの存在が伝わる**（#151 の方針に反する）。

| | 条件 | 満たさないとき |
|---|---|---|
| 送る人 | WS のメンバーで、ページを読める（#97） | 拒否（`Forbidden`） |
| 送られる人 | 同じ WS のメンバーで、ページを読める | `mentionUser`: `MENTION_USER_DOC_ACCESS_DENIED`。コメント: その人にだけ送らない |
| 通知・メールのタイトル | **サーバーが台帳（`doc_meta.title`）から取る** | 送る側から来た値は使わない |

⚠️ **判定はサーバーで行う。** 画面ではページを開けない人は `@` を押せないが、
`mentionUser` は GraphQL の API なので、画面を通らず直接呼べる。以前はログインしているかしか
見ておらず、誰でも任意のユーザーに、タイトルを偽った通知とメールを送れた（#223）。

対象の経路（すべて同じ判定を通す）:

| 経路 | 通知 |
|---|---|
| `mentionUser`（本文の `@`） | `Mention` |
| `createComment` / `createReply` の `mentions` | `CommentMention` |
| `createReply` の親コメントの作者 | `Comment` |

⚠️ ワークスペースの Owner は、ページ単位の制限があっても読める（`getDocRole`）。
サーバー全体 Admin は、WS のメンバーでなくても `getDocRole` を素通りするため、
**送られる人は WS のメンバーであることを別に確かめる**。

### `@` のメニューに「Invite…」は無い（#223）

AFFiNE には、`@` のメニューの「Invite…」（設定のメンバー画面を開く）と、
拒否されたときの「Invite」ボタン（ページの閲覧権限を付けて送り直す）があった。
どちらも消した。

- メンションの相手は WS のメンバーなので、招待は関係ない。メンバーを増やす入口は設定のメンバー画面だけ
- メンション操作で権限が変わるのは予想しにくい。権限は共有メニューで変える

### `@` のメニューの「メンバーをメンション」に出る候補（#220）

| 打ち込んだ文字 | 出る候補 |
|---|---|
| **無し**（`@` だけ） | 自分 ＋ **自分以外の先頭 2 人** |
| あり | 名前が一致するメンバー（最大 3 人表示、それ以上は「N 人のメンバーがいます」） |

⚠️ 以前は、打ち込んだ文字が無いとメンバーを**一度も読み込まず**、自分と「Invite…」しか出なかった（#220）。
ほかの画面（共有メニューの招待欄など）は開いたときに読み込んでいた。文字が無くても読み込む（`search('')`。
語が空なら全員が対象で、先頭から 8 人）。

⚠️ 自分以外の 2 人は、**自分を除いてから**先頭 2 人を取る。先に 2 人取ってから自分を除くと、
自分が先頭 2 人に入っていたときに 1 人しか出ない（以前の動き）。

## 2. ⚠️ 「通知済み」の印は書かない（#217・2026-09-13 決定）

AFFiNE では、通知を送ったあと、メンションの属性に通知の ID（`mention.notification`）を書き込んでいた。
ofuro-wiki では**書かない**。

| | 事実（2026-09-13 コードで確認） |
|---|---|
| バックエンドの戻り値 | 通知の ID ではなく `true` |
| BlockSuite の検査 | `notification: z.string().optional()`（`.catch(undefined)` 付き）。`true` は通らず、属性ごと捨てられて**空の書き換え＝何も起きない** |
| 結果 | **印は一度も書き込まれていなかった**。メンション自体は消えない |
| 印を読む箇所 | 印を書く直前の判定だけ（ほかに無い） |

読む側が無いため、書く処理ごと消した。動きは以前と同じ（印は書かれない）。
将来「通知済み」を使う機能を作るなら、そのときにバックエンドが ID を返すか、決まった文字列を書く。
