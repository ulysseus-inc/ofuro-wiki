# シングルサインオン（SSO / OIDC）の設定

ofuro-wiki は **OpenID Connect (OIDC)** によるシングルサインオンに対応しています。
社内で使っている ID 基盤（Google Workspace・Microsoft Entra ID・Keycloak 等）の
アカウントで ofuro-wiki にサインインできるようになります。

> **動作確認済み**: Keycloak、Google Workspace（「内部」で公開したアプリ）
> **対応見込み**: Microsoft Entra ID、Okta、その他の OIDC 準拠プロバイダ
> （OIDC 標準に準拠して実装しています。未検証のため、問題があればご報告ください）

---

## 全体の流れ

設定は **3ステップ**です。

1. **ofuro-wiki 側でリダイレクト URI を確認する**（コピーする）
2. **IdP 側でアプリケーションを登録**し、クライアント ID とシークレットを取得する
3. **ofuro-wiki 側に発行者 URL・クライアント ID・シークレットを入力**して有効化する

> 💡 設定は**管理画面から行い、`.env` の編集やサーバーの再起動は不要**です。

---

## ステップ1: リダイレクト URI を確認する

管理画面 →「**サーバー設定**」→「**シングルサインオン（OIDC）**」を開きます。

「**リダイレクト URI**」に表示されている値を、コピーボタンで控えてください。

```
https://wiki.example.com/oauth/callback
```

> ⚠️ **この値は IdP 側にそのまま登録する必要があります。** 1文字でも違うと認証が失敗します。
> 表示される値は `BASE_URL` 環境変数から生成されます。`BASE_URL` が実際の
> アクセス URL と異なっていると、この値も誤ったものになります。

---

## ステップ2: IdP 側でアプリケーションを登録する

お使いの IdP に応じて進めてください。

### Google Workspace / Google アカウント

1. [Google Cloud Console](https://console.cloud.google.com/) でプロジェクトを作成（または既存のものを選択）
2. **「API とサービス」→「OAuth 同意画面」** を設定
   - ユーザーの種類: 社内利用なら「**内部**」（Google Workspace の場合）
   - スコープの追加は不要（`openid` / `email` / `profile` のみ使用）
3. **「API とサービス」→「認証情報」→「認証情報を作成」→「OAuth クライアント ID」**
   - アプリケーションの種類: **ウェブ アプリケーション**
   - **承認済みのリダイレクト URI**: ステップ1でコピーした値を貼り付け
   - 「承認済みの JavaScript 生成元」は**空のままで構いません**（トークン交換はサーバー側で行うため）
4. 発行された **クライアント ID** と **クライアント シークレット** を控える

> ⚠️ **「外部」を選んだ場合は、「テストユーザー」に検証用のアドレスを登録してください。**
> 登録しないと `403 access_denied` で弾かれます。ここが最もつまずきやすい箇所です。
> 「内部」であればこの登録は不要で、**組織のメンバーだけがサインインできます**。

> 💡 **開発環境と本番環境では、クライアントを分けることを勧めます。**
> 1つのクライアントにリダイレクト URI を複数登録しても動きますが、
> 開発用のシークレットは本番より緩い場所に置かれがちです。分けておけば、
> 開発用だけを失効・再発行できます。
>
> なお Google は `http://localhost` のリダイレクト URI を例外的に許可しているため、
> **HTTPS もデプロイも無しに、手元で検証できます**（例:
> `http://localhost:8080/oauth/callback`）。

ofuro-wiki 側に入力する発行者 URL:

```
https://accounts.google.com
```

> ⚠️ **一般の Google アカウント（gmail.com）を許可する構成では、
> 「未登録の利用者を SSO サインイン時に自動作成する」を必ず OFF にしてください。**
> ON にすると、Google アカウントを持つ誰でもサインインできてしまいます。
>
> 逆に **Workspace の「内部」で公開したアプリなら、ON にして問題ありません**。
> 組織のメンバー以外は Google 側で弾かれるためです。

### Microsoft Entra ID（旧 Azure AD）

> **未検証です。** OIDC 標準に準拠しているため動作する見込みですが、
> 問題があればご報告ください。

1. Microsoft Entra 管理センター →「**アプリの登録**」→「**新規登録**」
2. **リダイレクト URI**: プラットフォームに「Web」を選び、ステップ1の値を入力
3. 「**証明書とシークレット**」→「**新しいクライアント シークレット**」を作成し、値を控える
   - ⚠️ シークレットの値は作成直後にしか表示されません
4. 「**概要**」からアプリケーション（クライアント）ID とディレクトリ（テナント）ID を控える

ofuro-wiki 側に入力する発行者 URL（**テナント固有の v2.0 エンドポイント**）:

```
https://login.microsoftonline.com/<テナントID>/v2.0
```

> ⚠️ **`common` は使わないでください。** issuer にプレースホルダが含まれるため、
> 検証に失敗します。必ずテナント ID を含む URL を指定してください。

> ⚠️ Entra ID は `email` クレームを返さないことがあります。サインイン時に
> 「メールアドレスを取得できませんでした」と表示される場合は、ofuro-wiki 側の
> 「**メールアドレスのクレーム名**」に `upn` を追加してください（例: `email,upn`）。

### Keycloak

1. 対象の realm →「**Clients**」→「**Create client**」
   - Client type: `OpenID Connect`
   - Client ID: 任意（例: `ofuro-wiki`）
2. **Capability config**
   - `Client authentication`: **On**（機密クライアントにする）
   - `Standard flow`: On
3. **Login settings**
   - `Valid redirect URIs`: ステップ1でコピーした値
4. 作成後、「**Credentials**」タブから **Client secret** を控える

ofuro-wiki 側に入力する発行者 URL:

```
https://keycloak.example.com/realms/<realm名>
```

### Okta

> **未検証です。**

1. Admin Console →「**Applications**」→「**Create App Integration**」
   - Sign-in method: **OIDC - OpenID Connect**
   - Application type: **Web Application**
2. **Sign-in redirect URIs**: ステップ1でコピーした値
3. 発行された **Client ID** と **Client secret** を控える

発行者 URL:

```
https://<your-domain>.okta.com
```

## ステップ3: ofuro-wiki 側で設定する

管理画面 →「サーバー設定」→「シングルサインオン（OIDC）」で入力します。

| 項目 | 内容 |
|------|------|
| **発行者 URL（Issuer）** | ステップ2で確認した URL。`/.well-known/openid-configuration` は**付けない** |
| **クライアント ID** | IdP で発行された値 |
| **クライアントシークレット** | IdP で発行された値（保存後は再表示されません） |
| **ボタンの表示名** | サインイン画面のボタンに出る文字（例: `Google でサインイン`） |
| **メールアドレスのクレーム名** | 既定は `email` のみ。通常は変更不要（後述の注意を参照） |
| **未登録の利用者を SSO サインイン時に自動作成する** | 後述 |

> ⚠️ **`preferred_username` を安易に追加しないでください。**
> アカウントの紐付けはメールアドレスの一致で行うため、**利用者が自分で
> 値を変更できる項目**（多くの IdP のユーザー名がこれに当たります）を
> 追加すると、他人のアドレスを名乗って**既存アカウント（管理者を含む）に
> サインインされる**恐れがあります。
> 追加してよいのは、**IdP が管理していて利用者が書き換えられない項目**
> （Entra ID の `upn` など）だけです。

### 「接続をテスト」で確認する

有効化する前に「**接続をテスト**」を押してください。
発行者 URL が正しければ、IdP の情報が取得できたことが表示されます。

失敗する場合は、発行者 URL の綴り、ネットワーク（ファイアウォール）、
IdP 側の公開設定を確認してください。

### 有効化する

「**シングルサインオンを有効にする**」を ON にすると、サインイン画面にボタンが表示されます。

> 💡 発行者 URL・クライアント ID・シークレットのいずれかが未入力の場合、
> 有効にしてもボタンは表示されません（設定途中の状態で利用者が失敗しないようにするため）。

---

## 「未登録の利用者を SSO サインイン時に自動作成する」の判断

**この設定は、お使いの IdP の性質によって正解が逆になります。**

| IdP の性質 | 推奨 | 理由 |
|---|:--:|---|
| 社内の利用者しかいない（Entra ID・Keycloak・Google Workspace の内部限定） | **ON** | 入社した人がすぐ使える |
| 社外の人も利用できる（一般の Google アカウント等） | **OFF** | **ON にすると、その IdP でサインインできる誰もが利用可能になる** |

**既定は OFF（自動作成しない）** です。OFF の場合、あらかじめ管理画面でアカウントを
作成しておく必要があります（メールアドレスが一致すれば SSO で紐付きます）。

---

## 運用上の注意

### SSO で作成されたアカウントはパスワードを持ちません

自動作成されたアカウントにはパスワードが設定されないため、
**パスワード認証ではサインインできません**（SSO 経由のみ）。

### 既存アカウントとの紐付けはメールアドレスで行います

IdP 側のメールアドレスと、ofuro-wiki 側のアカウントのメールアドレスが
一致した場合に同じアカウントとして扱われます（**大文字・小文字は区別しません**）。

> 大文字違いのアカウントが複数存在する場合は、どれを本人とみなすか
> 決められないため、サインインを拒否します（取り違えを防ぐため）。
> その場合は管理画面で重複を整理してください。

> ⚠️ **信頼できる IdP のみを設定してください。**
> メールアドレスで既存アカウントに紐付ける仕組みのため、
> 「誰でも任意のメールアドレスを名乗って登録できる IdP」を設定すると、
> **他人のアカウント（管理者を含む）を乗っ取られる恐れ**があります。
>
> ofuro-wiki は IdP が `email_verified` クレームで「未確認」と明示した場合は
> サインインを拒否します。ただし、このクレームを返さない IdP（Microsoft Entra ID 等）も
> あるため、最終的には**設定した IdP を信頼できるか**の判断が必要です。

### バックエンドは1インスタンス構成が前提です

サインインの途中経過（認可リクエストの照合情報）はバックエンドの
メモリ上に保持しています。**ロードバランサ等でバックエンドを複数台に
分散すると**、認証の開始と復帰が別のプロセスに振り分けられ、
「サインインの有効期限が切れています」と表示されて必ず失敗します。

標準の配布構成（単一コンテナ）ではこの問題は起きません。

### 別のアカウントに切り替えるには、IdP 側でサインアウトします

一度 SSO でサインインすると、**IdP 側にセッションが残ります**。以降は
「SSO でサインイン」を押しても入力を求められず、同じアカウントで認証されます
（再入力が不要なのは SSO 本来の利点です）。

そのため、**別のアカウントに切り替えたい場合は、IdP 側でサインアウト**してください。

| IdP | サインアウト先 |
|-----|---------------|
| Google | [https://accounts.google.com](https://accounts.google.com) → 該当アカウントからログアウト |
| Microsoft Entra ID | [https://portal.office.com](https://portal.office.com) などからサインアウト |
| Keycloak | `https://<Keycloakのホスト>/realms/<realm名>/account` → サインアウト |

> 💡 個人アカウントと業務アカウントを併用している場合、意図しない方で
> サインインしてしまうことがあります。**「未登録の利用者を SSO サインイン時に
> 自動作成する」が ON だと、その時点でアカウントが作られます。**
> 不要なアカウントができた場合は、管理画面から削除してください。

> ⚠️ **共有 PC では注意してください。** 前の利用者が IdP にサインインしたままだと、
> 次の人が SSO ボタンを押しただけで前の利用者として入れてしまいます。
> これは SSO 全般の性質で、IdP 側のセッション有効期限やサインアウト運用で対処します。

### `JWT_SECRET` を変更するとシークレットの再入力が必要です

クライアントシークレットは `JWT_SECRET` から派生した鍵で暗号化して保存されます。
`JWT_SECRET` を変更すると復号できなくなり、SSO は「未設定」として扱われます
（サインイン画面のボタンも消えます）。その場合はシークレットを入力し直してください。

### SSO を無効にしても、既存の利用者は残ります

「シングルサインオンを有効にする」を OFF にすると、ボタンが消えるだけです。
SSO で作成されたアカウントは残りますが、パスワードを持たないため
**サインインできなくなります**。必要に応じて管理画面からパスワード再設定用の
URL を発行してください。

## うまくいかないときは

| 症状 | 確認すること |
|---|---|
| サインイン画面にボタンが出ない | 「有効にする」が ON か / 発行者 URL・クライアント ID・シークレットがすべて入力済みか |
| `redirect_uri_mismatch` エラー | IdP 側に登録した URI が、管理画面に表示されている値と**完全に一致**しているか（`http`/`https`、末尾のスラッシュ、ポート番号） |
| 「メールアドレスを取得できませんでした」 | 「メールアドレスのクレーム名」に `upn` を追加（特に Entra ID） |
| 「このメールアドレスのアカウントがありません」 | 自動作成が OFF。管理画面でアカウントを作成するか、自動作成を ON にする |
| 「サインインの有効期限が切れています」 | 認証画面を開いたまま10分以上放置した場合に出ます。やり直してください（毎回出る場合は、バックエンドを複数台で動かしていないか確認）|
| 別のアカウントで入り直せない | IdP 側にセッションが残っています。上記「別のアカウントに切り替えるには」を参照 |

---

## 開発者向け: ローカルでの検証

開発用の Keycloak を同梱しています（通常の起動では立ち上がりません）。

```bash
docker compose --profile dev up -d keycloak
```

設定値・テストユーザーは [`docker/keycloak/README.md`](../docker/keycloak/README.md) を参照してください。
