# インポート仕様

外部ファイルを ofuro-wiki のドキュメントとして取り込む機能の仕様。

対象: `frontend/packages/frontend/core/src/desktop/dialogs/import/index.tsx`（画面）と
`frontend/blocksuite/affine/shared/src/utils/file/filesys.ts`（ファイル選択）。

---

## 1. 対応形式

| 種類 | 拡張子 | 複数選択 | 備考 |
|---|---|:--:|---|
| Markdown | `.md` `.markdown` | ○ | |
| Markdown + 画像 | `.zip` | × | 画像を同梱した zip |
| HTML | `.html` `.htm` | ○ | |
| Notion エクスポート | `.zip` | × | Notion の HTML エクスポート |
| Word | `.docx` | × | |
| スナップショット | `.zip` | × | ofuro-wiki 自身のエクスポート |

> `.affine` ファイルのインポートは **Electron 版専用**のため、
> Web 版（ofuro-wiki の提供形態）では選択肢に出ない。

---

## 2. ファイル選択の方式

**`<input type="file">` を使う。File System Access API（`showOpenFilePicker`）は使わない。**

### なぜ File System Access API を使わないか

インポートに必要なのは**ファイルの中身を一度読むこと**だけで、
書き戻しをしないためファイルハンドルを保持する必要がない
（実際、取得したハンドルは直後に `getFile()` して捨てていた）。

一方で File System Access API には以下の実害があった。

- **UNC パス（`\\wsl.localhost\...` 等）のファイルを選ぶと失敗する**（Issue #86）。
  WSL 上のファイルがインポートできず、Windows 側にコピーすると成功する、という症状になる。
- Safari・Firefox は非対応で、どのみち `<input type="file">` の経路が必要。
  **2経路あると、片方だけが壊れていても気づきにくい。**

`<input type="file">` は権限モデルもパス解決も持たないため、この問題が発生しない。

### `accept` 属性には MIME と拡張子の両方を書く

```
accept="text/markdown,.md,.markdown"
```

**MIME だけでは不十分。** `.md` に MIME を登録していない OS（Windows が典型）では、
`accept="text/markdown"` だけだとファイル選択ダイアログに `.md` が一件も表示されない。

## 3. エラーの扱い

ファイル選択の結果は3通りあり、**それぞれ区別して扱う**。

| 結果 | 表示 |
|---|---|
| ファイルを選んだ | インポートを実行 |
| キャンセルした | 「ファイルが選択されていません」 |
| 選択自体が失敗した | **失敗した理由をそのまま表示** |

> **区別しないと何が起きるか（Issue #86 の実害）**
> 以前は失敗もキャンセルも同じ `null` を返していたため、
> **エラーで失敗しているのに「ファイルが選択されていません」と表示され**、
> 利用者は自分の操作ミスだと誤解した。原因はブラウザのコンソールにしか出ていなかった。
>
> **原因が画面に出ないエラー表示を作らないこと。**

インポート処理そのもの（パース・変換）の失敗は、従来どおり例外のメッセージを表示する。

### 呼び出し元の義務

`openFilesWith` はインポート画面だけでなく、**画像の挿入・添付ファイル・
マインドマップの取り込み**からも呼ばれる。**すべての呼び出し元が例外を受け止めること。**

| 呼び出し元 | 受け止め方 |
|---|---|
| エラー表示を自前で持つ（インポート画面・`import-doc` ウィジェット） | その仕組みに流す |
| 持たない（画像・添付・マインドマップ） | `notifyFileOpenFailed(std, err)` で通知する |

`notifyFileOpenFailed` は `filesys.ts` にある共通処理で、コンソールへの出力に加えて
**画面にトーストを出す**。

> **なぜ義務なのか**
> 以前は Chrome では例外が内部で握りつぶされ、この関数は事実上「絶対に失敗しない」
> ものとして扱えた。失敗を伝えるようにした以上、**受け止めない呼び出し元は
> 未処理の rejection になり、利用者からは「押しても何も起きない」ようにしか見えない。**
> それは Issue #86 で起きたことそのものであり、直した先で作り直してはいけない。

読み込み中の表示など**UI の状態を立ててから呼ぶ場合は `finally` で必ず戻す**こと
（戻さないとスピナーが消えなくなる）。

## 4. 画面

| 状態 | 表示 |
|---|---|
| `idle` | 形式の一覧 |
| `importing` | 進行中 |
| `success` | 完了 → ドキュメントを開く |
| `error` | エラー内容 + 「再試行」 |

エラー画面に**外部への問い合わせ導線は置かない**。
セルフホスト製品であり、問い合わせ先は導入した組織の管理者であるため
（AFFiNE 由来の Discord リンクが空 URL のまま残り、押しても無反応だった）。
