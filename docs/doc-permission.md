# ページ単位の権限

Issue #97。「役員限定ページ」「人事情報ページ」を作れるようにする。

現状は**ワークスペース全体のロールだけが機能**しており、
**ワークスペースのメンバーは全ドキュメントを読める**。

関連: [`doc-level-permission-dead-code.md`](doc-level-permission-dead-code.md)（前提調査）/
Issue #148（招待の受諾に穴がある）

---

## ⚠️ 最初に — この機能の本質

> ## **「読めない」ではなく「存在を知られない」**

**本文を隠すだけでは足りない。** 権限の無いドキュメントは、
**あることすら分からない**状態にする。

| 漏れる場所 | 何が伝わるか |
|---|---|
| ドキュメント一覧 | **タイトル**・更新日時 |
| 検索結果 | **タイトル・本文の抜粋**・ヒット件数 |
| 最近更新した一覧 | タイトル・更新日時 |
| バックリンク（#101） | **リンク元にタイトルが出る** |
| 件数表示 | 「全 128 件」の数字が変わる |

> `人事評価_2026Q3` — **タイトルだけで中身が推測できる。**
> ヒット件数だけでも「そういう文書が存在する」ことが伝わる。

**実装するときは、常にこの一覧を意識する。**
「本文を返していないから大丈夫」は誤り。

### 認可は2種類ある（2026-08-07 追加）

**この2つを分けて考える。** 混ぜていたことが、下記の未完部分を生んだ。

| | 問い | 対象 |
|---|---|---|
| **Read Authorization** | 本文を**読んでよいか** | ドキュメントの中身 |
| **Discovery Authorization** | その存在を**知ってよいか** | ドキュメントの目次・件数・タイトル |

社内 Wiki が必要とするのは**両方**である。とりわけ後者。
「査定_2026下期_田中」のようなタイトルは、**それ自体が情報**であり、
中身が見えなくても漏洩になる。

> **⚠️ フォーク元 AFFiNE は Read しか実装していない。**
>
> 一覧は `rootYDoc.getMap('meta').get('pages')`（ワークスペース共有の Yjs 目次）
> から作られ、**権限外ページのタイトルも全メンバーに同期される**。
> `Doc_Read` を見ているのは「開いたとき」「プレビュー」「バックリンク」
> 「モバイル詳細」の4箇所だけで、**一覧には無い**。
> バックリンクは権限の無い項目を*消さず*「アクセス不可」に差し替える
> ——**存在は見せる**という一貫した方針である。
>
> 構造上の理由もある。目次が CRDT の共有ドキュメント1個であるため、
> **行単位で人ごとに出し分けられない。** 上流は「そこまではやらない」と
> 決めている。ofuro-wiki は**その決定に従わない**。

### ⚠️ 現在の実装状況（v0.1.0 時点）

| | 状態 |
|---|---|
| **Read Authorization** | **完了。** 本文・履歴・検索・REST・`get-markdown`・権限API・監査ログ |
| **Discovery Authorization** | **未完。** ドキュメント一覧にタイトルが残る |

**未完の理由は実装漏れではなく、データモデルと要求仕様の衝突である。**

```
rootYDoc
  └─ meta.pages          ← ワークスペース全体で共有される CRDT
       ├─ 公開ページA
       ├─ 人事評価_田中   ← ここを人ごとに出し分けられない
       └─ 役員会議録
```

サーバー API（`workspaceDocs` 等）は正しく絞っている。
**画面の一覧がその API を見ておらず、共有 Yjs 目次から作られている。**

**採らなかった案（2026-08-07 決定）**

制限したページを共有目次から削除し、権限者にはサーバー問い合わせの結果を
合流させて見せる案を検討したが、**却下した**。

削除そのものは重くない（権限変更時に1回）。問題は**見せる側**である。
目次から外したページはクライアントのデータモデルから消えるため、
タグ・コレクション・お気に入り・並べ替え・クイック検索が効かなくなる。
つまり**権限を持つ人（役員）だけ Wiki がまともに使えない**。
そして制限ページが増えるほど、
**「共有 Yjs 目次」と「権限者用のサーバー目次」の二重管理**に育つ。
最終的に下記の設計変更をやることになり、二重の経路を抱えた分だけ高くつく。

**進め方**: 本 Issue（#97）は Read Authorization を完成させて閉じる。
Discovery Authorization は
**「Workspace Document Index を認可可能なサーバー管理モデルへ移行する」**
として別 Issue に切る。

#### ⚠️ 「一覧の取得元を変える」では解決しない

**漏洩源は UI がどこを読むかではない。`rootYDoc` そのものが全員に
同期されていることである。** 一覧を Server Index から取るようにしても、
Yjs にタイトルが残っていれば**開発者ツールから普通に読める。**

```
Server Index
  └─ 人事評価_田中 → 権限なし → 返さない   ← ここだけ直しても

rootYDoc
  └─ meta.pages
       └─ 人事評価_田中 → 全員に同期        ← ここから漏れる
```

**要件はこう書く。**

> **権限外ドキュメントの Discovery Metadata（title / tags / timestamps 等）を、
> `rootYDoc` からクライアントへ同期しない。**
> **Discovery Metadata の source of truth を Server Document Index へ移す。**

「一覧を Server から取得する」ではなく、**source of truth の移動**である。

最終形:

```
Yjs
  └─ 本文・編集状態・リアルタイム同期

Server Document Index          ← Discovery Metadata の source of truth
  └─ id / title / tags / dates / owner ...
       ↓
       PermissionService
       ↓
       ユーザーごとの可視 Document 集合
```

この分離は今回の権限問題だけでなく、**部門別 Wiki・非公開フォルダ・
個人ページ・役員限定・人事限定・プロジェクト限定**にも自然に対応できる。

#### ⚠️ 権限を外した「あと」の失効

7章はサーバー側の判定キャッシュを扱っている。**Discovery には別の問題がある。**

```
10:00  A さん   → 人事評価ページを見る（タイトルがブラウザに届く）
10:01  管理者   → A さんの権限を None にする
10:02  A さん   → ブラウザに古いタイトルが残っている
```

**「存在を知られない」を厳密に採るなら、配信済みのものも失効させる。**
次 Issue に以下を要件として含める。

| 残る場所 | 失効のさせ方 |
|---|---|
| **`rootYDoc` の `meta.pages`** | **最重要。** ここに残る設計は採らない |
| Document Record（フロントの実体） | 権限変更の通知で破棄 |
| Discovery Index のキャッシュ | 同上 |
| 最近使ったページ | ローカル状態から除去 |
| クイック検索のローカル状態 | 同上 |
| WebSocket 接続中の状態 | 接続を切るか、購読から外す |

> **要件**: 権限変更・解除時に、**対象ユーザーの Discovery Metadata を失効させる。**
> とりわけ**権限剥奪後も Yjs 側にタイトルが残る設計は採らない。**

## 1. なぜこの機能を作るのか（判断の経緯）

**2026-08-06 に「本当に必要か」を議論し、実装すると判断した。** 経緯を残す。

### 1.1 出た問い

> ofuro-wiki はワークスペースをいくつでも作れ、そこで権限を設定できる。
> **「権限はワークスペース単位です。これが製品仕様です」と言い張れないのか。**

もっともな問いである。**言い張れている実例は実在する。**

| 製品 | 権限の粒度 | 立て付け |
|---|---|---|
| **esa.io** | チーム全体（記事単位の権限なし） | **「情報は共有されるべき」という思想として明示** |
| **Cosense（Scrapbox）** | プロジェクト単位 | 同上。**リンクで繋がること**を価値の中心に置く |

どちらも国内で支持されている製品で、**機能不足ではなく思想として主張**している。

### 1.2 それでも作ると判断した理由

**ofuro-wiki は、この2社と立ち位置が違う。**

| | esa / Cosense | **ofuro-wiki** |
|---|---|---|
| 訴求 | オープンな共有・アイデアの連結 | **セルフホスト・外部送信ゼロ・情シス審査を通る** |
| 客層 | 開発チーム・スタートアップ | **法人の情シス** |

[`feature-gap-analysis.md`](feature-gap-analysis.md) の競合マトリクスは、こう結論している。

> **SSO・監査ログ・ページ単位権限は「ほぼ全社が持っている」— 差別化要素ではなく参加資格。**
> **ここが ✕ である限り、法人の情シス審査を通らない**

**「情シス審査を通る」を掲げる以上、審査票の項目に ✕ を付けることになる。**
esa の思想を借りるなら訴求そのものを変える必要があり、**両立しない。**

### 1.3 「いま作る」理由

**先送りするほど高くつく。**

認可は**今後のすべての機能に付いて回る**。#96（添付ファイル内検索）・#101（バックリンク）・
#100（閲覧ログ）——いずれも「権限外を出さない」実装と検証が要る。

| | 経路の数 | 難易度 |
|---|:--:|---|
| **いま** | **16** | 全部を一度に見渡せる |
| 機能が倍になった後 | 30以上 | **既存機能すべてに retrofit** |

> ⚠️ **議論の途中で「継続コストが高いから見送る」と述べたが、これは逆だった。**
> 継続コストが高いことは、**先に入れる理由**である。基本機能は、システムが単純なうちに入れる。

### 1.4 検討して採らなかった代替案

**「ワークスペース = アクセスグループ」として運用する**案（役員WS・人事WS を分ける）。
管理は数個で収まり、Confluence の Space・Notion の Teamspace と同じ発想で標準的でもある。

**採らなかったのは、実装を確認した結果、Wiki の中核価値が切れるため。**

| 確認したこと | 実測（2026-08-06） |
|---|---|
| **ドキュメント間リンク** | `ReferenceInfoSchema` は **`pageId` のみ**を持ち `workspaceId` が無い → **ワークスペースをまたげない** |
| **全文検索** | `searchWithDSL(workspaceId, ...)` で**ワークスペース単位**。横断検索の API は存在しない |

```
全社Wiki（100ページ）から、役員限定の3ページを別ワークスペースへ
  → その3ページへリンクが張れない
  → 検索しても出てこない（別ワークスペースを開いて検索し直す）
  → サイドバーの階層構造から外れる
```

**「たどれること」が Wiki の価値の中核**であり、そこが切れる。

> なお esa・Cosense も同じ制約を持つ（チーム・プロジェクトをまたげない）。
> 彼らはそれを受け入れているが、**それは「分ける必要がない」思想とセットだから**である。

## 2. 権限の粒度 — ワークスペース単位とドキュメント単位

**「粒度が細かくなるだけ」ではない。認可の性質そのものが変わる。**
実装に入る前に、この4点を理解しておく必要がある。

### 2.1 ⚠️ 認可の場所が「入口」から「出口」へ移る（最も重要）

ワークスペース単位は **Guard** で守れる。**「このリクエストを通すか」を真偽で答えれば済む**からである。

```ts
// workspace-member.guard.ts
async canActivate(context): Promise<boolean>   // ← 通す / 通さない の二択
```

**ドキュメント単位はここでは守れない。**
一覧や検索は「リクエストは通すが、**返す結果のうち一部を落とす**」必要がある。
Guard は**返す中身を知らない**ので判定できない。

| | ワークスペース単位 | **ドキュメント単位** |
|---|---|---|
| 実装場所 | **Guard**（横断・1箇所） | **データを組み立てる各所** |
| 判定 | 通す / 通さない | **1件ごとに残す / 落とす** |
| 守り漏れの見え方 | Guard を付け忘れる（**付いていないので分かる**） | **絞り忘れる**（動いてしまうので分からない） |

**「1箇所で守れるもの」から「全部の出口で守るもの」に変わる。** これが本 Issue の難しさの本体である。

### 2.2 「許可の集合」から「許可と拒否の混在」へ

| | ワークスペース単位 | ドキュメント単位 |
|---|---|---|
| 既定 | メンバーなら**全部見える** | ワークスペースのロールを**継承** |
| 例外 | 無い | **`None` で遮断できる** |

**例外が入ると、例外の適用漏れが漏洩になる。**
現在は「メンバーか否か」の二値なので、例外そのものが存在しない。

### 2.3 漏れたときの見え方が違う

| | ワークスペース単位 | ドキュメント単位 |
|---|---|---|
| 漏れると | **他人のワークスペースが丸ごと見える** | **一覧に1行余計に出る** / 検索に1件ヒットする |
| 気づくか | **すぐ気づく** | **気づかない** |

`#47`（H-1 IDOR）は前者で、E2E も書きやすい性質だった。
今回は**「出ていないこと」を確かめる**テストになり、書き方が変わる。

### 2.4 「存在を隠す」要件が新しく出る

ワークスペース単位では、非メンバーには**最初から何も見えない**。

ドキュメント単位では**同じワークスペースに居る**ため、本文を隠しても
**タイトル・件数・更新時刻が漏れる**。

**これは現在の設計には無い概念**であり、本書の冒頭に置いた理由でもある（→ 冒頭の表）。

### 2.5 取り消しの即時性

| | ワークスペース単位 | ドキュメント単位 |
|---|---|---|
| 権限を外したとき | メンバー削除 → **接続を切れば済む** | **そのドキュメントだけ**切る必要がある |

接続は生きたまま、特定ドキュメントの権限だけ消える。7章のキャッシュはここに効く。

### 2.6 ⚠️ 保護フラグ（#66）とは別物

**どちらも「編集できなくする」ため混同されやすいが、まったく別の機能である。**
[`doc-read-only-protection.md`](doc-read-only-protection.md) の位置づけをそのまま引き継ぐ。

| 観点 | **保護フラグ（#66・実装済み）** | **ページ単位の権限（#97・本書）** |
|---|---|---|
| 目的 | **誤操作の防止** | **セキュリティ境界** |
| 実体 | ドキュメントのプロパティ（**Yjs で同期**） | **サーバーが強制**する権限 |
| 誰が変えられる | **編集権限を持つ全員** | `Doc_Users_Manage` を持つ者だけ |
| 解除 | **本人が OFF にすれば即編集可** | 権限の変更が必要 |
| 読めなくできるか | ❌ **できない**（読めるが編集できないだけ） | ✅ **`None` で読めなくできる** |
| 例え | **うっかり防止のカバー** | **鍵** |

> **#66 があっても「この人には見せない」は実現できない。** そこが本 Issue の範囲である。

### 実装上の注意

**保護フラグを認可の判定に混ぜないこと。**

`Doc_Update` の可否は**権限だけ**で決める。保護フラグはクライアント側の
「緩いロック（advisory lock）」であり、**サーバーの認可条件にしてはいけない。**

理由は2つ。

1. **保護フラグは Yjs で同期される＝利用者が自由に書き換えられる。**
   サーバーの判断材料にすると、**利用者が自分で外して回避できる**ものを
   セキュリティ境界として扱うことになる
2. **役割が違う。** 保護フラグが ON でも、権限のある人は自分で OFF にして編集してよい。
   それが #66 の設計意図（誤操作の防止であって、制限ではない）

両者は**独立した軸**として並存する。

```
権限 = Editor  かつ  保護フラグ = ON
  → サーバーは編集を許可する（Doc_Update ✅）
  → 画面が「保護モードが有効です」と警告する（#66 の役割）
  → 本人が保護を外せば、そのまま編集できる
```

## 3. なぜ今は「制限」ができないのか

`PermissionService.canReadDoc` の最後の1行がすべてである。

```ts
const role = await this.getDocRole(workspaceId, docId, userId);
return role !== null;     // ← ロールが何であれ null でなければ読める
```

`getDocRole` は `DocPermission` が無ければ**ワークスペースのロールに落ちる**ため、
**メンバーは必ず何らかのロールを持ち、必ず読める。**

`none` を入れても `null` ではないので、やはり読めてしまう。
**つまり `DocPermission` は「昇格」しかできず、「制限」ができない。**

`DocMeta.defaultRole` は列としては存在するが、**認可では一度も読まれていない。**

## 4. モデル

### 4.1 ロール

`schema.ts` の `DocRole` に合わせる。

| ロール | 意味 |
|---|---|
| `Owner` | そのドキュメントの所有者 |
| `Manager` | 権限を含めて管理できる |
| `Editor` | 編集できる |
| `Commenter` | コメントだけできる |
| `Reader` | 読める |
| **`None`** | **アクセス不可**（← 役員限定ページの実現手段） |
| `External` | 公開共有からの閲覧者（**→ 下記。通常の実効ロールではない**） |

### 4.2 実効ロールの決め方

> **⚠️ ここが認可の中核。認可バグは評価順序でほぼ発生する。**
> **段数を増やさない。** 「継承・明示許可・明示拒否」が混在すると、
> 実装もテストも保守も難しくなる。

**2段階＋バイパス**で決める。これ以上増やさない。

```
① バイパス:  サーバー全体 Admin なら、判定せずに全許可
                （運用上の最終手段。組織を跨いだ復旧・調査のため）

⓪ 前提:      ワークスペースのメンバーでなければ、その時点で不許可
                （doc に設定があっても通さない）

② 下限:      ワークスペースの管理者（owner / admin）なら Owner
                （自分のワークスペースから締め出さないため。→ 下記）

③ 実効ロール = ドキュメントの設定 ?? ワークスペースのロール
                └─ あれば「完全に置換」する。無ければワークスペース
```

#### ② 管理者の下限について（2026-08-07 追加）

**当初は無かった。** 「ドキュメントの設定が置換する」だけにしていたところ、
**既定ロールを `None` にした本人（ワークスペースの所有者）が自分の
ワークスペースの文書から締め出され、サーバー全体 Admin しか復旧できない**
状態になった。**E2E で検出**（単体テストはこの組み合わせを持っていなかった）。

隠す相手は「同じワークスペースの**一般の利用者**」であって、そのワークスペースの
管理者ではない。管理者はバックアップからも DB からも読めるため、
**ここで隠しても境界にならない**。隠せているつもりになる分、むしろ有害である。

> **⚠️ `DocMeta.defaultRole` は NULL 可であること。** NULL が「未設定」を表す。
> 既定値（かつて `'reader'`）を入れると**全 doc が「設定済み」になり**、
> ③ で常にドキュメントの設定が勝つため、**所有者を含む全員が降格する。**
> これも E2E で初めて出た。

#### Admin のバイパスについて（2026-08-06 決定）

**サーバー全体 Admin は、役員限定ページも含めてすべて読める。** これを許容する。

| 案 | 判断 |
|---|---|
| **A. バイパスあり（採用）** | **標準的な形。** バックアップ・復旧・調査は Admin にしかできず、ここを塞ぐと運用が詰む |
| B. Admin も権限に従う | 却下。**障害時に復旧できなくなる** |
| C. バイパス + 閲覧を監査ログに残す | **将来 #100（閲覧ログ）で自然に実現される。** 現在の監査ログは更新系のみで、読んだことは記録していない |

> ⚠️ **運用上の含意**: 人事情報も役員議事録も、**Admin 権限を持つ人には見える**。
> Admin を誰に与えるかが、そのままアクセス範囲の決定になる。
> `ADMIN_EMAIL` と `is_admin` の付与は、**権限設計の一部として扱うこと。**

> ⚠️ **⓪ を忘れないこと。**
> 「doc の設定が置換する」を素直に実装すると、**ワークスペースのメンバーでない人でも
> `DocPermission` があれば通ってしまう。**
> **ワークスペースに居ることは、すべての前提条件**である（真理値表（10章）の 6・7）。

**「ドキュメントの設定」は1つの層**として扱う。その中の優先順位は次の1行だけ。

```
ドキュメントの設定 = DocPermission[利用者]  ??  DocMeta.defaultRole
```

| 判定 | 意味 |
|---|---|
| `DocPermission[利用者]` がある | **その人だけの設定**。最優先 |
| 無く `defaultRole` がある | **そのドキュメントの既定**（全員に効く） |
| どちらも無い | ワークスペースのロールを使う |

```
役員限定ページの作り方:
  DocMeta.defaultRole = None        ← 既定を「アクセス不可」に
  DocPermission(役員A) = Reader     ← その人だけ許可
  DocPermission(役員B) = Reader
```

#### なぜ「置換」なのか（`min` を取らない）

ドキュメントの設定は、**ワークスペースのロールを完全に置き換える。**
`min(ワークスペース, ドキュメント)` のような合成はしない。

- 合成にすると**判定が2変数の関数**になり、真理値表が倍に膨らむ
- 「置換」なら**「その doc に設定があるか？」のみ**を見ればよい

**結果として、ワークスペースのロールより強い権限も与えられる**
（`reader` の人に、この doc だけ `Editor`）。これは意図した挙動である。

> 設定できるのは `Doc_Users_Manage` を持つ者（= その doc の Owner / Manager）だけであり、
> その権限自体はワークスペースの owner / admin から来る。**昇格の起点は管理者にある。**

#### 3段階にしない理由（検討の記録）

当初は `Admin → DocPermission → defaultRole → ワークスペース` の**4段**にしていた。
レビュー（2026-08-06）で「評価順序が複雑で、認可バグはここで起きる」と指摘され、改めた。

**やったことは「段を減らす」ではなく「まとめる」。**
`DocPermission` と `defaultRole` は**どちらも『その doc の設定』**であり、
別の段として並べるから複雑に見えていた。1つの層に畳めば、
外から見た評価は **「doc の設定があるか、無いか」の2択**になる。

> ⚠️ **`defaultRole` を読むことが本 Issue の中核であることは変わらない。**
> ここが抜けると「制限」が実現できず、昇格しかできない今のままになる。

### 4.3 ワークスペースのロールとの対応

| ワークスペース | ドキュメント |
|---|---|
| `owner` / `admin` | `Owner` |
| `member` | `Editor` |
| `reader` | `Reader` |

`getDocRole()` も `External` を返さない。**表の上だけに存在する到達不能な行**である。
公開共有を実装するときに、上記の専用経路として作ること。
> 公開ページから社内の運用情報が漏れるのを防ぐ。

## 6. ⚠️ 経路の網羅（本 Issue で最も危険な部分）

**1箇所漏れると情報漏洩になる。**

### 6.0 判定は `PermissionService` に集中させる

**各経路が書いてよいのは「呼ぶこと」だけ。**

```ts
// ✅ これだけ
if (!(await this.permission.canRead(workspaceId, docId, userId))) throw ...;

// ❌ 経路側にロジックを書かない
if (role === 'owner' || role === 'manager' || (role === 'editor' && ...)) { ... }
```

**各 Resolver が `if` や `switch` を書き始めると、半年後に破綻する。**
同じ判断が各所に散らばり、**片方だけ直った状態**が生まれる。それが漏洩になる。

`PermissionService` が公開するのは次の3種類だけにする。

| 種類 | 用途 | 例 |
|---|---|---|
| **1件の可否** | 単一ドキュメントを返す経路 | `can(workspaceId, docId, userId, 'Doc_Read')` |
| **複数の絞り込み** | 一覧・バックリンク | `filterReadable(workspaceId, docIds, userId)` |
| **問い合わせ条件** | **検索（6.3）** | `readableDocCondition(workspaceId, userId)` |

> ⚠️ **アクション名（`Doc_Read` 等）以外の語彙を経路側に持ち込まない。**
> 「Owner なら」「Manager 以上なら」を経路に書いた時点で、
> 権限マトリクス（5章）が唯一の正でなくなる。

### 6.2 表と実装のずれを機械的に検知する

**人の注意力に頼らない。**

`docs/logging.md` の記録一覧と同じ方式で、**表に無い経路が増えたらテストが落ちる**ようにする。

- Socket.IO は `@SubscribeMessage` を、REST は `@Get`/`@Post` を、GraphQL は
  `@ResolveField`/`@Query` をソースから集める
- **本表に載っていない経路があれば失敗させる**

> **同種の見落としを、#117 の作業中だけで4回踏んでいる**
> （#145 入口の取り違え / #146 compose の未配線 / #147 REST 経路の記録漏れ /
> #149 検証条件の甘さ）。**#97 は1回漏れれば情報漏洩になる。**

### 6.3 ⚠️ 検索は「検索**前**に絞る」

**取ってから捨ててはいけない。**

```
❌ 10,000件を検索 → 9,999件を捨てる → 1件返す
✅ 読める doc に絞る → その中で検索 → 1件返す
```

理由は2つあり、**2つ目が決定的**である。

**1. 性能。** 捨てる前提で全件を走査するのは無駄が大きい。

**2. ⚠️ ページングが壊れる。**

```
「20件ください」→ 20件取得 → 権限で15件捨てる → 5件しか返らない
次のページ → ずれる / 抜ける / 重複する
```

**後から捨てる方式では、件数もページも正しくならない。**
「全 128 件」の表示も嘘になり、しかも**その数字自体が存在を漏らす**（冒頭の表）。

#### やり方

権限の判定を **SQL の条件として表現**し、全文検索の `WHERE` に混ぜる。
`DocPermission` も `DocMeta` も**同じ PostgreSQL にある**ため、素直に書ける。

```
PermissionService.readableDocCondition(workspaceId, userId)
  → 検索クエリに差し込む条件（doc_id の絞り込み）
```

> ⚠️ **「読める doc の ID を配列で渡す」方式は採らない。**
> ドキュメントが数千・数万になると配列が巨大になり、
> **件数が増えるほど遅くなる**（本来は逆であるべき）。

これは **6.0 の「問い合わせ条件」** にあたる。
一覧・バックリンク・#96（添付ファイル内検索）・#100（閲覧ログ）でも同じものを使う。

### 6.5 エクスポートは2種類ある — 混同しない

「エクスポート」と一言で書くと権限を誤る。**別物として扱う。**

| | **ワークスペースの一括エクスポート** | **1ドキュメントのエクスポート** |
|---|---|---|
| 実体 | `POST /api/workspaces/:ws/export`（zip） | 画面から Markdown / HTML / PDF で保存 |
| 中身 | **そのワークスペースの全ドキュメント** | 開いている1件だけ |
| 必要な権限 | **ワークスペースの `owner` / `admin`** | **`Doc_Copy`**（= Reader でも可） |

**一括エクスポートは、権限で隠したドキュメントも zip に入る。**
ドキュメント単位で絞ると「一部が欠けたバックアップ」になり、
復元したときに**静かにデータが消える**。したがって**絞らず、実行者を絞る。**

> ⚠️ **`Doc_Read` を持つ人が1件をエクスポートするのは止められない。**
> 画面に表示できている時点で、選択してコピーもできる。
> **技術的に防げないものを「防いだつもり」にしない**（`Doc_Copy` は Reader に ✅ としてある）。
>
> 持ち出しを追いたい場合は**禁止ではなく記録**で対応する（#100 閲覧ログ）。

### 6.6 Blob（画像・添付ファイル）は doc 単位で絞らない

**判断: ワークスペースのメンバーであれば取得できる。** 現状どおりとする。

| 理由 | 内容 |
|---|---|
| **紐付けが無い** | `blobs` は**どの doc に貼られているか**を持たない。同じ画像が複数の doc から参照されうる |
| **鍵が推測できない** | 取得には blob の鍵（コンテンツハッシュ）が要る。**その鍵は doc を読めた人しか知り得ない** |

> ⚠️ **これは「安全だから」ではなく「割に合わないから」の判断である。**
> 鍵を知っている人（＝以前その doc を読めた人）は、**権限を外された後も画像を取得できる。**
>
> 塞ぐには blob と doc の対応表が要り、**参照が消えたときの追跡**まで必要になる。
> 本文が読めなければ文脈も分からないため、**残存リスクは小さい**と判断した。
>
> **必要になったら別 Issue で対応する。** ここに書いてあるのは「見落とし」ではなく「判断」である。

### 6.7 awareness（カーソル・編集中の表示）も doc 単位で絞る

**書き漏らしていた経路。** 段階0 の網羅テストが検出した（2026-08-06）。

`space:update-awareness` / `space:load-awarenesses` は **`docId` を受け取り、
その doc の部屋へ配信する。** 本文は流れないが、**次が漏れる。**

| 漏れるもの | 何が伝わるか |
|---|---|
| 参加者の一覧 | **誰がその doc を開いているか** |
| カーソル位置・選択範囲 | **編集が行われていること**、おおよその文書量 |

> 「役員が3人で何かを編集している」——**本文が読めなくても、これは情報である。**
> 冒頭に書いた「**存在を知られない**」に真正面から反する。

したがって **`Doc_Read` を要求する。**

> ⚠️ **この経路は、私が仕様書を書いたときに見落としていた。**
> 「本文が流れないから対象外」と無意識に判断していた。
> **網羅テストを先に作る（段階0）方針が、実装前に効いた実例である。**


### 6.8 権限が無いときは 404 を返す（403 ではない）

**「存在するが権限が無い」と返してはいけない。**

```
403 Forbidden  → 「そのドキュメントは存在する」と伝わる
404 Not Found  → 存在自体が分からない
```

冒頭に書いた「**存在を知られない**」に従い、**読めない doc は「無い」ものとして扱う。**

> ⚠️ ただし**書き込み系で 404 を返すと、利用者が混乱する**
> （「さっきまで編集できたのに消えた？」）。
> Socket.IO の編集経路は `ACCESS_DENIED` を返す。
> **読み取りは隠し、書き込みは断る**、と使い分ける。

### 6.4 将来の機能でも同じ入口を通す

ofuro-wiki は AI 機能（AI 検索・要約・ナレッジグラフ）を将来的に検討している。
それらは**必ず「読めるドキュメントの集合」を必要とする。**

**いま `readableDocCondition` / `filterReadable` を用意しておけば、
将来の機能はそれを通すだけで済む。**

> ⚠️ 逆に、経路ごとに独自の絞り込みを書くと、
> **AI 機能が権限を無視して全文を読む**という最悪の形になりうる。
> 「AI に情報を渡さない Wiki」を掲げる以上、ここは外せない。

**いま実装する必要はない。** `PermissionService` の責務として意識しておく。

## 7. 性能

`sync.gateway` の `checkWorkspaceAccess` は**ワークスペース単位・キャッシュ付き**。
ドキュメント単位に落とすと、**判定の粒度と回数が変わる。**

| | 現在 | 変更後 |
|---|---|---|
| 判定単位 | ワークスペース | **ドキュメント** |
| 頻度 | 接続時に1回 | **`load-doc` ごと・`push-doc-update` ごと** |

`push-doc-update` は**打鍵のたびに飛ぶ**ため、毎回 DB を引くと現実的でない。

**方針**: 実効ロールを**接続ごと・ドキュメントごとにキャッシュ**し、
権限の変更時に**明示的に捨てる**（`grantDocUserRoles` 等の実行時）。

> ⚠️ **キャッシュの寿命だけに頼らないこと。** 「権限を外したのに、
> 相手のタブでは編集が続けられる」状態が生まれる。
> **権限変更時に、その利用者の接続を切るか、キャッシュを無効化する。**

## 8. GraphQL 操作

`.gql` が実在する＝**フロントが既に呼ぶ前提**の操作。

| 操作 | 必要な権限 |
|---|---|
| `grantDocUserRoles` | `Doc_Users_Manage` |
| `revokeDocUserRoles` | `Doc_Users_Manage` |
| `updateDocUserRole` | `Doc_Users_Manage` |
| `updateDocDefaultRole` | `Doc_Users_Manage` |
| `workspace.doc.defaultRole` | `Doc_Read`（**→ 下記**） |
| `workspace.doc.grantedUsersList` | `Doc_Users_Read` |
| `workspace.doc.permissions` | `Doc_Read` |

> **⚠️ `defaultRole` は `Doc_Users_Read` にしない。**
>
> 「誰が見られるか」と「既定の権限レベル」は別物である。
>
> | 項目 | 判定 | 理由 |
> |---|---|---|
> | `grantedUsersList` | `Doc_Users_Read` | **個人が特定できる。** 役員限定ページの閲覧者一覧から人事異動が推測できる |
> | `defaultRole` | `Doc_Read` | **文書の属性であって、誰の情報でもない。** 読める人が既定のレベルを知っても漏れるものが無い |
>
> `defaultRole` は**共有メニューを開くたびに要求される項目**
> （`getWorkspacePageById`）であり、`Doc_Users_Read` を課すと
> **Editor / Reader が共有メニューを開いた時点で落ちる。**

**フロントの権限 UI について**（当初「`display:none` で封印されている」と書いたが、
**これは誤りだった**）:

`share-menu.tsx` の `display: 'none'` は Invite / Members **タブの見出し**に
付いており、上流 AFFiNE の設計そのものである（見出しを隠し、共有メニュー内の
行をクリックして遷移させる作り）。**封印ではないので、解除すべきものは無い。**

権限 UI（`MembersPermission` / `DocGrantedUsersService`）は最初から生きており、
`useGuard('Doc_Users_Manage')` で出し分けている。**動かなかったのは
バックエンドが値を返していなかったためで、フロントの変更は要らない。**

## 9. 監査ログ

権限の変更は**必ず記録する**（[`logging.md`](logging.md) の記録一覧に追加）。

| action | 実行者 | 対象ID | 対象名 | 記録経路 |
|---|:--:|:--:|:--:|---|
| `doc.permission.grant` | ✅ | ✅ | — | Interceptor |
| `doc.permission.revoke` | ✅ | ✅ | — | Interceptor |
| `doc.permission.role` | ✅ | ✅ | — | Interceptor |
| `doc.permission.default` | ✅ | ✅ | — | Interceptor |

> **対象名（doc のタイトル）は残さない。** Interceptor は引数しか見ないため、
> タイトルを引くには別途問い合わせが要る。`doc.publish` / `doc.restore` など
> 既存の doc 系も同じ扱いで、対象は ID で追う。
>
> **代わりに「誰に配ったか」は残す。** `detail.meta` に `userIds` と `role` が入り、
> **漏洩の範囲を特定できる**。ここが無いと監査ログとして意味を成さない。

**「誰がいつ、誰に何を見せるようにしたか」が追えないと、情報漏洩の調査ができない。**

## 10. ⚠️ 認可の真理値表（必須のテスト）

**経路の網羅（6章）とは別に、判定そのものを組み合わせで固定する。**

6章は「**塞ぎ忘れた経路が無いか**」を見る。
本節は「**判定そのものが正しいか**」を見る。**両方要る。**

### なぜ要るか

`PermissionService` は今後も書き換わる（性能改善・キャッシュ・条件式化）。
**そのたびに壊れていないことを保証できないと、誰も触れなくなる。**

真理値表があれば、**内部をどう書き換えても、外から見た振る舞いが固定される。**

### 表の軸

| 軸 | 値 |
|---|---|
| ワークスペースのロール | `owner` / `member` / `reader` / 非メンバー |
| `DocMeta.defaultRole` | 未設定 / `None` / `Reader` / `Editor` |
| `DocPermission[利用者]` | 無し / `None` / `Reader` / `Editor` / `Manager` |
| サーバー全体 Admin | 真 / 偽 |

**30〜50ケースを目安**に、各ケースで `Doc_Read` / `Doc_Update` / `Doc_Delete` /
`Doc_Users_Manage` を確認する。

### 必ず入れるケース

| # | ワークスペース | doc 既定 | 利用者個別 | 期待 |
|---|---|---|---|---|
| 1 | `member`(Editor) | 未設定 | 無し | Read ✅ / Update ✅ （**従来どおり**） |
| 2 | `member`(Editor) | **`None`** | 無し | **Read ❌**（← 役員限定ページ。**これが本 Issue の目的**） |
| 3 | `member`(Editor) | **`None`** | `Reader` | **Read ✅ / Update ❌**（個別に許可） |
| 4 | `reader`(Reader) | 未設定 | `Editor` | **Update ✅**（doc の設定が**置換**する） |
| 5 | `member`(Editor) | 未設定 | **`None`** | **Read ❌**（その人だけ外す） |
| 6 | 非メンバー | `Reader` | 無し | **Read ❌**（**ワークスペースに居ないなら見えない**） |
| 7 | 非メンバー | 未設定 | `Reader` | **Read ❌**（同上。**doc だけ許可しても入れない**） |
| 8 | 何でも | 何でも | 何でも | **Admin は必ず ✅**（バイパス） |

> ⚠️ **6・7 を落とさないこと。** ワークスペースのメンバーでない人に
> doc の権限を与えても、**アクセスさせてはいけない**。
> 「doc の設定が置換する」を素直に実装すると、**ここが通ってしまう**。
> **ワークスペースのメンバーであることは、すべての前提条件**である。

## 11. やらないこと

| やらないこと | 理由 |
|---|---|
| フォルダ単位の権限の継承 | ドキュメント単位で足りる。継承は判定が複雑になり、漏れの温床になる |
| グループ（部署）単位の付与 | 利用者単位で始める。必要になってから足す |
| 権限の期限 | 運用が複雑になる。まず基本形を確実に |
| ワークスペースをまたぐリンク・検索 | 1.4 の代替案を採らないため不要。**やるなら別 Issue** |
